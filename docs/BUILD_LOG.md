# Rave-OS Build Log

A running record of how Rave-OS gets built: decisions made, concepts learned, and what exists at each stage. This log exists because the project is also how the author is learning x86 assembly and C — code alone doesn't capture the reasoning.

## Vision

Rave-OS is a custom operating system in C, C++, and assembly. Visually it fuses 90s pixel art with rave/acid-graphics (demoscene, Amiga, plasma/hue-cycling palettes). It draws inspiration from the book *Build Your Own Operating System* by Lucas Darnell. Initial target is x86/x64 running as a VM guest.

Ambitions beyond the visuals:
- A mouse-driven GUI (own windowing system).
- Its own dialect of Forth as a core language.
- Self-hosting — Rave-OS eventually recompiles its own source from within itself.

These can't happen all at once, so the project is staged:

1. **Bootable groundwork** — bootloader, minimal kernel, framebuffer output on x86/x64-as-VM.
2. **Mouse-driven GUI / windowing layer.**
3. **Rave-OS's own Forth dialect.**
4. **Self-hosting** (OS recompiles its own source).

ACIDSTORM (`demos/acidstorm/`), a Robotron/Llamatron-inspired twin-stick shooter, is a demo game that ships bundled with Rave-OS — it established the acid pixel-art visual language early on and continues to exist as an included application, not a phase that gets discarded.

## 2026-08-02 — Toolchain setup (Stage 1 begins)

Decisions made:
- **Compiler:** use the container's existing `gcc` with freestanding flags (`-ffreestanding -nostdlib -fno-pie -m32`) rather than building a dedicated `i686-elf` cross-compiler. Verified this host gcc can compile freestanding 32-bit object code without a separate cross-compiler build — good enough for now; revisit a real cross-compiler only if host-toolchain assumptions cause real problems later.
- **Bootloader:** hand-write our own 16-bit real-mode boot sector in NASM assembly rather than relying on GRUB/Multiboot. More work, but this is where a lot of the x86 assembly learning (BIOS interrupts, the A20 line, GDT setup, the real-mode → protected-mode switch) actually happens, and it fits the from-scratch spirit of the project.
- **Bit width:** start in 32-bit protected mode (the classic path — simpler segmentation/paging, smaller step up from 16-bit real mode) before attempting 64-bit long mode as a later stage.

Installed in the `forth-os` container: `nasm` (assembler), `qemu-full` (provides `qemu-system-i386`/`qemu-system-x86_64` for running the OS as a VM guest).

Next up: write the first boot sector — a 512-byte program BIOS loads at `0x7C00`, printed text via BIOS interrupt `int 0x10`, ending in the `0xAA55` boot-signature — and run it in QEMU.

## 2026-08-02 — First boot sector runs

`boot/boot.asm` is Rave-OS's first piece of real code: a hand-written x86 boot sector, assembled with NASM, that boots successfully in QEMU.

**How a BIOS boot sector works, and what the code does:**
- On power-on, the BIOS (here, QEMU's SeaBIOS) reads the first 512-byte sector off the boot disk into memory at physical address `0x7C00`, and — *only if* the last two bytes of that sector are the magic value `0xAA55` — jumps the CPU to `0x7C00` in **16-bit real mode**. Real mode is the same addressing/execution mode the original 8086 used: 16-bit registers, no memory protection, no paging. Every x86 CPU still starts here for backward compatibility, even 64-bit ones.
- `BITS 16` / `ORG 0x7C00` tell NASM to assemble 16-bit instructions and calculate label addresses as if the code is loaded at `0x7C00` (needed since we use labels like `msg` that must resolve to real addresses).
- `cli` disables interrupts while we point the segment registers (`ds`, `es`, `ss`) at segment 0 and set up a stack (`sp = 0x7C00`, growing downward into free memory below the boot sector) — doing this with interrupts on risks a hardware interrupt firing mid-setup with a half-configured stack. `sti` re-enables interrupts once that's done.
- The message-printing loop uses `lodsb` (load byte at `[ds:si]` into `al`, then auto-increment `si`) to walk the null-terminated string `msg`, calling BIOS interrupt `int 0x10` function `0x0E` ("teletype output") once per character — the simplest way to get text on screen without touching video memory or a driver directly.
- On hitting the string's `0` terminator, it jumps to an infinite `cli` / `hlt` / `jmp` loop — `hlt` stops the CPU until the next interrupt, and looping back to another `hlt` keeps it parked rather than falling through into whatever garbage bytes follow.
- `times 510 - ($ - $$) db 0` pads the file with zero bytes up to offset 510 (`$` is "here", `$$` is the section start, so `$-$$` is bytes emitted so far) — then `dw 0xAA55` writes the boot signature as the final two bytes, giving exactly 512 bytes total. BIOS refuses to boot a sector without this signature.

**Testing approach:** rather than relying on a visible QEMU window, the build uses QEMU's monitor (`-display none -monitor unix:/tmp/qemu-mon.sock,server,nowait`) and sends `screendump /tmp/shot.ppm` over that socket via `socat`, then converts the PPM to PNG (`python-pillow`) to inspect. This is fully scriptable/non-interactive, which matters for later stages too. `imagemagick`'s `convert` was tried first but is currently broken in this container (`GLIBC_2.44 not found` — a version mismatch in the container's package set); `python-pillow` worked as a substitute.

Files: `boot/boot.asm`, `boot/Makefile` (`make` assembles `boot.bin` via `nasm -f bin`; `make run` boots it in `qemu-system-i386`).

Next up: this boot sector currently just prints and halts. The next real milestone is switching from 16-bit real mode into 32-bit protected mode — setting up a Global Descriptor Table (GDT), enabling the A20 line, and making the jump — as the foundation for running actual C kernel code.

## 2026-08-02 — Two-stage bootloader + 32-bit protected mode

A single 512-byte sector isn't enough room for GDT setup, a protected-mode switch, and (eventually) a C kernel, so this stage splits the boot process in two:

- **`boot/stage1.asm`** (renamed from the old `boot.asm`, still the MBR boot sector at `0x7C00`): prints a message, then uses BIOS `int 0x13` function `0x02` ("read sectors", CHS addressing) to read the next `STAGE2_SECTORS` (2) sectors off the boot disk into memory at `0x0000:0x8000`, and far-jumps there. The boot drive number the BIOS passes in `dl` at entry is saved to a variable before the disk-read call clobbers `dl`, since we need it for `int 0x13`.
- **`boot/stage2.asm`** (loaded at `0x8000`, still starts in 16-bit real mode): does the actual real-mode → protected-mode transition:
  1. **Enable the A20 line** — on the original 8086, address bit 20 didn't exist, so addresses wrapped at 1MB; later chips added a gate (disabled by default at boot, for backward compatibility) that must be explicitly enabled to access memory above 1MB. Used the "fast A20" method: set bit 1 of I/O port `0x92`. (One of several historical methods — others go through the keyboard controller or BIOS `int 0x15` — this one is simplest and QEMU supports it.)
  2. **Build a flat GDT** (Global Descriptor Table) — protected mode requires a GDT describing memory segments before it can be entered. Built the minimal legal one: a required null descriptor, one code segment, one data segment, both base `0` / limit `0xFFFFF` with 4K granularity (→ 4GB) and 32-bit flag set, so segmentation is effectively a no-op and segment:offset addresses are just linear addresses.
  3. **Set `CR0.PE`** (bit 0 of control register 0, "Protection Enable") — this is the actual switch that turns on protected mode.
  4. **Far jump to the code segment selector** (`jmp CODE_SEG:protected_mode_entry`) — required immediately after setting `CR0.PE`: it's what flushes the CPU's prefetch queue (which may hold real-mode-decoded instructions) and loads `CS` with the new segment selector; falling through without a far jump leaves the CPU in a broken half-switched state.
  5. Once in 32-bit code (`BITS 32` from here on), load the other segment registers (`ds`/`es`/`fs`/`gs`/`ss`) from the data selector, set up a stack (`esp = 0x90000`), then **write directly to the VGA text-mode framebuffer at physical `0xB8000`** (2 bytes per character: ASCII byte + attribute byte) to prove protected mode is live — BIOS interrupts like `int 0x10` no longer work once real mode is left, since the BIOS's own interrupt handlers are 16-bit real-mode code.

Verified in QEMU via the same screendump technique as the first boot sector: all three expected messages appear (stage1's real-mode print, stage2's real-mode print, and the direct VGA write from 32-bit protected-mode code, visible overwriting SeaBIOS's own banner text at the top-left of the screen — the only way that text could appear there is if the write path used was the direct `0xB8000` framebuffer write, confirming the code executing it was really running in protected mode).

**Rough edge, noted for later:** `STAGE2_SECTORS` is a manually-synchronized constant in `stage1.asm` that must match stage2's actual padded size (currently hardcoded to exactly 1024 bytes via a `times` padding directive in `stage2.asm`) — if stage2 grows past that, both files need updating together. Fine for now; will likely need a more robust approach once stage2 needs to load a variably-sized C kernel.

Files: `boot/stage1.asm`, `boot/stage2.asm`, `boot/Makefile` (`make` builds `disk.img` = `stage1.bin` + `stage2.bin` concatenated; `make run` boots it in `qemu-system-i386`).

Next up: with protected mode working, the next milestone is bringing up a C kernel — compiling a freestanding C file, linking it with a custom linker script to a known address, and having stage2 jump into it instead of just printing and halting.

## 2026-08-02 — First C kernel boots

Added `kernel/` with Rave-OS's first C code, and wired stage2 up to load and jump into it instead of doing its own VGA print.

**Getting a C file to run with no OS underneath it:**
- `kernel/kernel_entry.asm` is a tiny 32-bit asm stub (`_start: call kmain` then halt-loop) that becomes the very first bytes of the kernel binary. A bare C file has no guaranteed "this is where execution starts at this exact address" property on its own — the linker script's `ENTRY(_start)` plus listing `kernel_entry.o` before `kernel.o` on the link line is what pins `_start` to the first byte.
- `kernel/kernel.c` is `kmain()`: writes `"Rave-OS kernel: hello from C!"` directly to the VGA text buffer at `0xB8000` (2 bytes/char: ASCII + color attribute), same technique used in raw asm for the protected-mode proof last stage, now from C. No `printf`, no libc — there isn't one linked in (`-nostdlib`).
- `kernel/linker.ld` places `.text`/`.rodata`/`.data`/`.bss` starting at `0x10000` — this has to match `KERNEL_LOAD_ADDR` in `boot/stage2.asm`, since stage2 jumps to that literal physical address. `.eh_frame`/`.comment`/`.note.*` are explicitly discarded since nothing loads/needs them and they'd otherwise bloat the flat binary.
- Compiled freestanding: `-m32 -ffreestanding -fno-pie -fno-stack-protector -fno-asynchronous-unwind-tables -nostdlib`. `-ffreestanding` tells gcc not to assume a hosted environment (no standard library, no `main` with argc/argv semantics); `-nostdlib` stops it linking against one; the rest suppress code (stack-protector canaries, exception-unwind tables) that assumes runtime support we don't have.
- `objcopy -O binary kernel.elf kernel.bin` strips all ELF metadata (headers, section table) down to just the raw loadable bytes — the CPU has no idea what an ELF file is; stage2 is just going to jump to a physical address and start executing whatever's there, so it needs to be the bare instruction bytes starting exactly at `_start`. Verified with `objdump -d kernel.elf` that `_start` disassembles at address `0x10000` as expected.

**Loading it off disk:** `boot/stage2.asm` now reads `KERNEL_SECTORS` (8, i.e. 4KB — generous headroom for now) more sectors starting at `KERNEL_START_SECTOR` (4, i.e. right after stage1's 1 sector + stage2's 2 sectors) into `0x1000:0x0000` (physical `0x10000`) via the same BIOS `int 0x13` mechanism as stage1 loading stage2 — still real mode, so BIOS disk services are still available at this point. *Then* it does A20 + GDT + `CR0.PE` + far jump, exactly as before, except the far jump target is now `KERNEL_LOAD_ADDR` (the kernel's `_start`) instead of stage2's own inline print-and-halt code.

**Known rough edge (unchanged from last stage, now touching 3 places instead of 2):** sector counts/offsets are manually-synced constants across `boot/stage1.asm` (`STAGE2_SECTORS`), `boot/stage2.asm` (`KERNEL_START_SECTOR`, `KERNEL_SECTORS`), and `kernel/Makefile` (`KERNEL_SECTORS`, used to pad `kernel.bin` to a whole number of sectors via `truncate`). This is fine while sizes are small and stable, but growing the kernel much further should probably come with a real fix — e.g. a build step that greps the actual compiled sizes and generates these constants automatically, or a stage2 that reads a size header instead of a hardcoded count.

Build: `boot/Makefile`'s `disk.img` target now depends on `kernel/kernel.bin` and invokes `make -C ../kernel` to build it, then concatenates `stage1.bin + stage2.bin + kernel.bin` — 512 + 1024 + 4096 = 5632 bytes total. `make -C boot clean` also cleans the kernel dir.

Verified end-to-end in QEMU: SeaBIOS → stage1 ("loading stage2...") → stage2 ("loading kernel...") → kernel prints its message in green and halts.

Next up: the kernel can currently only write directly to fixed VGA memory offsets. Reasonable next steps: a proper VGA text-mode driver (cursor tracking, scrolling, clear-screen) as a small first abstraction layer, and/or basic keyboard input (reading scancodes off the PS/2 controller) — both are groundwork before anything resembling the roadmap's GUI stage (see the Vision section at the top of this log).

## 2026-08-02 — VGA text-mode driver

Replaced the kernel's one-shot "poke bytes directly at 0xB8000" code with a real driver, `kernel/vga.c` / `kernel/vga.h`, giving `vga_clear()`, `vga_putc()`, `vga_puts()`, and `vga_set_color()`.

What it adds over the raw approach:
- **Cursor tracking** — a `cursor_row`/`cursor_col` pair advances as characters are written, instead of every caller having to compute its own screen offset.
- **Newline handling** — `\n` moves to column 0 of the next row (and `\r` alone just resets the column), rather than every string needing manual positioning.
- **Scrolling** — once `cursor_row` runs past the last row (25 rows in standard VGA text mode), `vga_scroll()` copies every row up by one (row *n* ← row *n+1*, for all rows) and blanks the new bottom row, so output behaves like a normal terminal instead of wrapping/overwriting row 0.
- **Hardware cursor** — VGA has an actual blinking cursor built into the card, controlled by writing a 16-bit position to two of its CRTC (CRT Controller) registers via I/O ports, not memory: index port `0x3D4` selects register `0x0E`/`0x0F` (cursor position high/low byte), then the value is written to data port `0x3D5`. This is the first code needing `outb`, so introduced `kernel/io.h` with `inb`/`outb` wrappers (`inline asm` around the `in`/`out` instructions) — this header will get reused by every future driver that talks to hardware over I/O ports (e.g. the keyboard, next).

`kernel/kernel.c` now just calls into this driver and proves scrolling works by printing 30 lines into a 25-row screen — verified in QEMU that only the most recent ~24-25 lines remain visible, with the earlier header messages correctly scrolled off the top, and the hardware cursor sitting on the new blank bottom row exactly where the next character would land.

Build note: linking now produces a `ld` warning ("LOAD segment with RWX permissions") — expected and harmless at this stage, since paging/segment permissions aren't set up yet, so there's no enforcement to conflict with anyway.

Files: `kernel/vga.c`, `kernel/vga.h`, `kernel/io.h`; `kernel/Makefile` updated to compile and link `vga.o` alongside `kernel.o`.

Next up: keyboard input — reading scancodes off the PS/2 controller (port `0x60`, using the new `inb`) — is the natural next driver, since `io.h` already exists for it and it's the next piece needed before anything interactive.

## 2026-08-02 — PS/2 keyboard driver

Added `kernel/keyboard.c` / `kernel/keyboard.h`: a polling-based PS/2 keyboard driver, and wired `kmain()` up to echo whatever's typed to the VGA driver.

**How PS/2 keyboard input works, no interrupts yet:**
- The keyboard controller has a status port (`0x64`) and a data port (`0x60`). Bit 0 of the status byte is "output buffer full" — set when the controller has a byte ready to read. `keyboard_read_scancode()` just spins (`while (!(inb(0x64) & 1)) {}`) until that bit is set, then reads the byte from `0x60`. This is polling rather than interrupt-driven — simpler to get right first, at the cost of burning CPU while waiting; using the keyboard IRQ instead requires an IDT (Interrupt Descriptor Table), which is a real future stage in its own right (also needed for exceptions, the timer, etc.), not a small addition to this one.
- The byte read is a **scancode**, not ASCII — specifically "scancode set 1", the legacy set the controller still emits by default for compatibility. Pressing a key sends its **make code**; releasing it sends the same value with the top bit set (**break code** = make code `| 0x80`). `keyboard_read_char()` masks that bit off to check `released`, and ignores break codes for every key except shift (see below).
- Two lookup tables (`scancode_to_ascii`, `scancode_to_ascii_shift`), indexed directly by make code, cover the main alphanumeric block (letters, digits, punctuation, space, tab, enter, backspace, escape). Entries of `0` mean "no printable character" — ctrl, alt, capslock, function keys, etc. aren't handled yet, and `keyboard_read_char()` just keeps polling past them rather than returning garbage.
- **Shift is tracked as state, not looked up in the table directly**: `SC_LSHIFT`/`SC_RSHIFT` (`0x2A`/`0x36`) update a `shift_held` flag on press/release instead of producing a character, and every other key's lookup picks the shifted or unshifted table based on that flag. This is the standard approach for any modifier key (ctrl, alt would work the same way) — the hard part of "keyboard input" is this kind of state tracking, not the port I/O itself.

**VGA driver got one addition to support this cleanly:** `vga_putc()` now handles `'\b'` (backspace) by moving the cursor back a column (wrapping to the previous row's last column if already at column 0) and blanking that cell, rather than printing byte `8` as a raw (garbage-looking) glyph.

**Testing an interactive driver without touching a real keyboard:** QEMU's monitor `sendkey` command injects synthetic key events into the guest (e.g. `sendkey a`, `sendkey backspace`, `sendkey shift-a` for a shifted combo) — sent over the same monitor socket used for `screendump`, with a short delay between each command so the guest's polling loop has time to consume each event before the next arrives (sending them with no delay between at all was tried first and didn't register — timing between injected events and the guest's poll loop matters). Verified: typing `a`, `b`, `c`, backspace, `d`, enter, then `shift-a` echoed exactly `abd` on one line and `A` on the next — confirming scancode reading, the backspace erase, and shift-modifier tracking all work correctly together.

Files: `kernel/keyboard.c`, `kernel/keyboard.h`; `kernel/vga.c` (backspace handling added to `vga_putc`); `kernel/kernel.c` now ends in a `keyboard_read_char()` → `vga_putc()` echo loop instead of halting; `kernel/Makefile` updated to build `keyboard.o`.

Next up: this closes out the immediate "bare-metal basics" work (VGA output + keyboard input). Bigger structural pieces still ahead before the GUI stage: an IDT for real interrupt-driven input (and exceptions), a memory allocator, and eventually paging. Worth deciding with the user which of those to tackle next, versus starting to sketch GUI-stage groundwork (VESA/VBE graphics mode) directly.

## 2026-08-02 — VESA/VBE linear framebuffer graphics mode

Jumped ahead to stage 2 (GUI) groundwork: switched the display from VGA text mode to a VESA BIOS Extensions (VBE) linear-framebuffer graphics mode, the foundation any pixel-based GUI needs. This is the first stage where stage2 (still real mode) and the kernel (protected mode) have to cooperate on something neither can fully do alone.

**Why this can't just be a kernel-side driver:** querying and setting a VBE mode requires BIOS `int 0x10` calls, which only work in real mode -- by the time the kernel runs, we're in 32-bit protected mode and the BIOS is unreachable. So the mode switch has to happen in stage2, *before* the protected-mode jump, and the resulting framebuffer details (physical address, pitch, resolution, bit depth) have to be handed to the kernel some other way.

**How the handoff works -- a fixed-address "boot info" struct:**
- `boot/stage2.asm`'s new `setup_video` calls VBE function `0x4F01` ("get mode info") for mode `0x112` (640x480, 32 bits/pixel), which fills a 256-byte `ModeInfoBlock` at a scratch address (`0x9000`). The fields that matter -- `PhysBasePtr` (offset `0x28`, the framebuffer's physical address), `BytesPerScanLine` (`0x10`), `XResolution`/`YResolution` (`0x12`/`0x14`), `BitsPerPixel` (`0x19`) -- get copied into a small packed struct at `0x9500`.
- It then calls VBE function `0x4F02` ("set mode") with mode `0x112 | 0x4000` -- that high bit tells VBE to use linear-framebuffer addressing (a single contiguous memory region) instead of the legacy bank-switched addressing scheme older VBE modes required.
- `kernel/boot_info.h` defines a C struct with the exact same layout at the exact same address (`0x9500`) -- since paging is off and segmentation is flat, both stage2's raw writes and the kernel's struct reads are just talking to the same physical memory, no coordination beyond "same address, same layout" required. This is the same trick as `KERNEL_LOAD_ADDR` from the previous stage: a hardcoded contract between the asm and C sides instead of a real IPC mechanism, because at this level there's no OS yet to provide one.

**The new graphics driver:** `kernel/graphics.c`/`graphics.h` provides `gfx_put_pixel()`, `gfx_clear()`, `gfx_width()`/`gfx_height()`, all reading geometry from `boot_info` rather than hardcoding it. `gfx_put_pixel` computes `framebuffer_addr + y*pitch + x*4` and writes a 32-bit packed color -- assumes XRGB8888 layout, which is what mode `0x112` conventionally provides in QEMU/Bochs VBE, but isn't verified against `RedFieldPosition`/etc. from the ModeInfoBlock yet (noted as a simplifying assumption, not a certainty for all VBE implementations).

**This obsoletes VGA text output for now:** switching video modes means `0xB8000` no longer behaves as VGA text memory, so `vga.c`'s text driver has nothing to write to anymore. `kernel.c` was rewritten to prove the new graphics path instead: it fills the whole 640x480 framebuffer with a classic demoscene XOR-plasma pattern (`r = x*255/w`, `g = y*255/h`, `b = (x^y)&0xFF`) -- cheap to compute, never repeats the same color in a neighboring pixel, and reads as unmistakably "acid," which is the whole visual point of the project. `vga.c` and `keyboard.c` are left in the tree (still compile, keyboard input still technically works) but have no visible output path until a graphics-mode bitmap font renderer exists -- noted as a real gap, not silently dropped.

**Also hardened the build:** `kernel/Makefile`'s `kernel.bin` target now checks the actual compiled size against the `KERNEL_SECTORS` byte budget *before* truncating, and fails loudly instead of silently chopping off real code if the kernel ever grows past it (this was a latent risk since the first two-stage-boot milestone; adding `graphics.o` made it worth fixing now rather than discovering it via a corrupted boot later).

Verified in QEMU via screendump: the full screen renders as a colorful magenta/green/purple XOR pattern with no BIOS text visible at all, confirming the mode switch, the boot_info handoff, and the framebuffer write path all work together correctly.

Files: `kernel/boot_info.h`, `kernel/graphics.c`, `kernel/graphics.h`; `boot/stage2.asm` (`setup_video`); `kernel/kernel.c` rewritten around the graphics driver; `kernel/Makefile` (adds `graphics.o`, size-check guard).

Next up: real text output in graphics mode needs a bitmap font renderer (interestingly, `demos/acidstorm/src/font.c` already has one that could potentially be ported/reused here) -- worth doing before going much further, since debugging future kernel work without any text output at all will get painful fast. After that: mouse input (PS/2 mouse, same controller family as the keyboard), then actual GUI primitives (windows, widgets).

## 2026-08-02 — Graphics-mode font renderer, ported from ACIDSTORM

Restored text output (lost when VGA text mode got replaced by the VBE framebuffer) by porting ACIDSTORM's font system into the kernel, rather than inventing a second, different font for Rave-OS -- the demo game and the OS now share one glyph set.

**What got ported vs. rewritten:**
- `kernel/font.c`/`font.h` is `demos/acidstorm/src/font.c`'s 5x7 dot-matrix glyph data and `font_glyph()` lookup, copied essentially verbatim -- same `G_A`..`G_Z`, `G_0`..`G_9`, punctuation tables. The **only** change: the original calls libc's `toupper()` (via `<ctype.h>`) to normalize case; the kernel has no libc (`-nostdlib`), so that one call would fail at link time. Replaced with a 3-line manual `raveos_toupper()`. This is the whole reason a straight `#include` of the original file wouldn't have worked -- everything else about the glyph format is identical.
- `kernel/text.c`/`text.h` (`text_puts()`, `text_width()`) is new, but deliberately mirrors ACIDSTORM's `gfx_text()`/`gfx_text_width()` (`demos/acidstorm/src/gfx.c`) formula-for-formula: each lit glyph dot becomes a `scale x scale` block, characters advance `6*scale` pixels (5 wide + 1 spacing), width is `n*6*scale - scale`. Kept identical on purpose so a size like "scale 2" means the same thing in both places.
- `kernel/graphics.c` gained `gfx_fill_rect()` (used by `text_puts` per glyph-dot, and now also by `gfx_clear`, which is just `gfx_fill_rect` over the whole screen -- a small simplification alongside the addition).

**Build-safety note:** adding `font.o`/`text.o` pushed the compiled kernel to 4749 bytes, over the previous `KERNEL_SECTORS=8` (4096-byte) budget -- and the size-check guard added last stage (rather than a stale build silently truncating real code) caught it immediately with a clear error. Bumped `KERNEL_SECTORS` to 12 (6144 bytes, headroom for near-term growth) in both `kernel/Makefile` and `boot/stage2.asm` (still the same manually-synced-constants rough edge noted twice already).

`kernel/kernel.c` now draws the XOR-plasma background as before, then overlays a centered white "RAVE-OS" title (scale 4) and a black "KERNEL: FONT RENDERER ONLINE" subtitle (scale 2) using `text_puts`. Verified in QEMU via screendump: both lines render correctly, legible over the plasma backdrop, confirming the font data, `text.c`'s layout math, and `gfx_fill_rect` all work together.

Files: `kernel/font.c`, `kernel/font.h` (ported), `kernel/text.c`, `kernel/text.h` (new); `kernel/graphics.c`/`.h` (`gfx_fill_rect` added); `kernel/kernel.c` (title/subtitle overlay); `kernel/Makefile` (`font.o`, `text.o`, bumped `KERNEL_SECTORS`); `boot/stage2.asm` (bumped `KERNEL_SECTORS` to match).

Next up: mouse input (PS/2 mouse, same controller/IRQ family as the keyboard) is the other GUI-stage essential still missing. After that, actual GUI primitives -- windows, widgets, an event loop -- start becoming meaningful, though an IDT for real interrupts (rather than polling) is worth revisiting before things get much more interactive.

## 2026-08-02 — PS/2 mouse driver, and a real bpp bug caught along the way

Added `kernel/mouse.c`/`mouse.h`: a polling PS/2 mouse driver, same family as the keyboard controller.

**How PS/2 mouse init/reading works:** the mouse is the 8042 controller's "auxiliary device" -- same two I/O ports as the keyboard (`0x60` data, `0x64` status/command), multiplexed. `mouse_init()` does the standard bring-up sequence: `0xA8` ("enable aux port"), read-modify-write the controller's configuration byte (`0x20`/`0x60` commands) to enable IRQ12 and the mouse clock, then `0xD4`-prefixed mouse commands `0xF6` ("set defaults") and `0xF4` ("enable data reporting"), each acknowledged with `0xFA`. Once streaming, the mouse sends 3-byte packets unprompted: byte 0's bits carry button states + sign bits for the X/Y deltas in bytes 1-2 (which need sign-extending from 8 bits to a real `int`), and bit 3 of byte 0 is always 1 -- used to resync if a read ever starts mid-packet. Status port bit 5 (`PS2_STATUS_AUX_DATA`) tells a waiting byte apart from a keyboard byte, since both devices' data arrives through the same output buffer; `read_mouse_byte()` discards anything not tagged as aux data rather than misreading a keystroke as mouse data.

**The bug this stage actually caught:** to visually prove the mouse worked, `kernel.c` needed a movable cursor (drawn via `gfx_fill_rect`, erased by recomputing the plasma backdrop color at the old position). Testing this in QEMU via `mouse_move`/`mouse_button` monitor commands showed no visible cursor at all -- and closer inspection of the *background* plasma pattern (present since the VESA/VBE milestone two entries up) showed it didn't match the intended XOR formula under any color-channel permutation, and even the on-screen text was rendering with visible RGB fringing once compared pixel-by-pixel. Root cause, found by temporarily rendering `boot_info`'s raw fields as hex text on screen (the font renderer paid for itself immediately here): `boot_info->pitch` was `0x780` = 1920 = `640*3`, not `640*4` -- meaning VBE mode `0x112` on this BIOS/QEMU actually reports **`BitsPerPixel = 24`**, not the 32 its standard VESA definition would suggest. `gfx_put_pixel()` had hardcoded a 4-byte word write at a 4-bytes/pixel stride; against an actual 3-bytes/pixel framebuffer, every single pixel write bled into the next pixel's bytes, corrupting the entire screen in a way that (by coincidence) still looked like a plausible, colorful "acid" pattern -- which is exactly why it went unnoticed through two prior milestones' screenshots.

**Fix:** `gfx_put_pixel()` now reads `boot_info->bpp` and writes exactly `bpp/8` bytes per pixel (byte-by-byte: blue, green, red, and a 4th padding byte only if `bytes_per_pixel >= 4`), instead of assuming a fixed 32-bit format. This is a more correct driver in general -- real VBE implementations do vary in reported bit depth -- not just a patch for this one BIOS's quirk.

Re-verified in QEMU with the same `mouse_move`/`mouse_button` sequence as before the fix: the plasma backdrop now renders as clean smooth gradients (no RGB fringing), the title/subtitle text is crisp, and a red 8x8 cursor square appears exactly where the simulated movements (right 100, down 60, left 40, then left-button-press) should place it -- confirming both the color fix and the mouse driver (movement, sign-extension, and button-state decoding) all work correctly together.

Files: `kernel/mouse.c`, `kernel/mouse.h` (new); `kernel/graphics.c` (`gfx_put_pixel` bpp fix); `kernel/kernel.c` (cursor tracking + plasma-restore erase, driven by `mouse_read_packet`); `kernel/Makefile` (`mouse.o`).

Next up: an IDT for real interrupts (keyboard/mouse currently both busy-poll, burning CPU and unable to do anything else concurrently) is the biggest structural gap before GUI primitives (windows, widgets, an event loop) become meaningful -- worth tackling before adding much more polling-based input/output code.

## 2026-08-02 — IDT, PIC, and interrupt-driven keyboard/mouse

Converted keyboard and mouse from busy-polling to real hardware interrupts: new `kernel/idt.c`/`idt.h` (Interrupt Descriptor Table), `kernel/pic.c`/`pic.h` (8259 PIC driver), and `kernel/isr.c` (the actual handlers + wiring).

**The IDT** is protected mode's equivalent of the real-mode interrupt vector table BIOS calls used back in `boot/stage2.asm` (`int 0x10`, `int 0x13`) -- a 256-entry table mapping vector number to handler address, loaded via the `lidt` instruction (the same idea as `lgdt` for the GDT, just a different table). `idt_set_gate()` builds one entry (handler address split into two 16-bit halves for historical reasons, a segment selector, and a type/flags byte); `KERNEL_CODE_SEGMENT` (`0x08`) has to match `CODE_SEG` from `boot/stage2.asm`'s GDT, since that's the segment already loaded into `CS` by the time kernel code runs.

**The PIC (8259)** is the chip that actually routes hardware IRQ lines to the CPU. Two of them exist (cascaded: the second/"slave" PIC's output feeds into the first/"master" PIC's IRQ2 line), and by power-on default they deliver IRQ0-15 at interrupt vectors `0x08`-`0x0F`/`0x70`-`0x77` -- which collide with CPU exception vectors (0-31) and had to be **remapped** (`pic_remap()`, the standard 4-command "ICW" initialization sequence) to `0x20`-`0x2F` instead. After remapping, every IRQ line is masked; callers unmask (`pic_clear_mask()`) only the ones they have a real handler for.

**Handlers use GCC's `__attribute__((interrupt))`** rather than hand-written assembly stubs: given a function shaped `void handler(struct interrupt_frame *frame)` (or with a leading `unsigned int error_code` for the handful of CPU exceptions that push one -- fixed by the architecture, encoded in `exception_has_error_code()`), the compiler generates the register save/restore and `iret` a real handler needs. Added `-mgeneral-regs-only` to `CFLAGS` globally, per GCC's own recommendation for these handlers -- there's no FPU/SSE state save around interrupt entry/exit, so any incidental use (even compiler-generated) would corrupt whatever the interrupted code was doing with those registers. The one thing this technique can't do: a handler has no way to know *which* vector invoked it (the CPU doesn't pass that in), so the generic exception/unused-IRQ catch-alls can halt-safely or send EOI, but can't report which specific exception or IRQ actually fired -- a real per-vector stub in assembly (pushing its own vector number before jumping to a shared dispatcher) would be needed for that. Noted as a rough edge, not fixed here, since the two IRQs that matter (1, 12) get real dedicated handlers regardless.

**keyboard.c and mouse.c** changed from "poll a port until a byte shows up" to "read from a small ring buffer that the IRQ handler fills, `hlt`-waiting (not busy-spinning) when it's empty" -- `keyboard_irq_push_scancode()`/`mouse_irq_push_byte()` are the only new surface the handlers in `isr.c` call. The scancode-to-ASCII translation and mouse packet decoding logic is unchanged from the polling versions. A nice side effect: with real separate IRQ1/IRQ12 vectors, the hardware itself now keeps the keyboard and mouse byte streams apart, so `mouse.c` no longer needs the old polling version's manual "check status port bit 5" disambiguation -- interrupts solve, in hardware, a problem software had to work around before.

**A real bug this caught:** `mouse_init()`'s handshake (still polling-based, run with IRQ12 masked so it can't race the new handler) reads two ACK bytes (`0xFA`) directly. First attempt at wiring this up produced a mouse cursor that jumped to a wildly wrong position, decoding a definitely-bogus packet. Tracing raw bytes (temporarily rendering them as hex via the font renderer -- paying for itself again) showed the very first "packet" byte read after enabling interrupts was `0xFA` -- the ACK byte, not a movement byte at all, but coincidentally also has bit 3 set (the bit `mouse_read_packet`'s resync check uses to recognize "start of a real packet"), so it slipped past unnoticed. Root cause: 8259 PICs latch an IRQ line's edge into their Interrupt Request Register even while that line is masked -- so polling a byte directly (bypassing the handler) while IRQ12 was masked left a *stale pending request* that fired the instant `interrupts_enable()` unmasked it, well after the byte it corresponded to had already been consumed. **Fix:** both `irq1_keyboard` and `irq12_mouse` now check the status port's "output buffer full" bit before trusting `inb(0x60)`, turning a spurious fire into a harmless no-op instead of a phantom byte. Re-verified with the same `mouse_move`/`mouse_button` sequence as the previous milestone: cursor lands exactly where expected again.

Build note: adding three more source files pushed the kernel past its `KERNEL_SECTORS` budget again (caught immediately by last stage's size-check guard, as intended) -- bumped from 12 to 20 sectors (10240 bytes) in both `kernel/Makefile` and `boot/stage2.asm`.

Files: `kernel/idt.c`, `kernel/idt.h`, `kernel/pic.c`, `kernel/pic.h`, `kernel/isr.c`, `kernel/interrupts.h` (new); `kernel/keyboard.c`/`.h`, `kernel/mouse.c`/`.h` (polling -> ring-buffer + IRQ push); `kernel/kernel.c` (calls `interrupts_init()` / `mouse_init()` / `interrupts_enable()` in that order, for the masking reason above); `kernel/Makefile` (`idt.o`/`pic.o`/`isr.o`, `-mgeneral-regs-only`, bumped `KERNEL_SECTORS`); `boot/stage2.asm` (bumped `KERNEL_SECTORS` to match).

Next up: actual GUI primitives (a window/rectangle abstraction, simple widgets, an event loop tying keyboard+mouse+graphics together) can now build on real interrupt-driven input. A proper compositor/backbuffer (flagged as a rough edge back in the mouse-driver stage) is worth doing before that gets far, so cursor/window movement doesn't corrupt whatever's underneath.

## 2026-08-02 — Offscreen backbuffer + present, real cursor compositing

Replaced "draw straight to video memory, and 'erase' by recomputing what the background formula should be" with a proper offscreen backbuffer and a single `gfx_present()` step that flips it to the real screen -- fixing, at the root, the cursor-corrupts-text bug flagged (and accepted, at the time) back in the mouse-driver stage.

**A discovery that shaped the design:** a backbuffer for 640x480x32bpp is ~1.2MB -- too big to just declare as a static C array without checking what that actually costs. Two problems surfaced on inspection:
1. `objcopy -O binary` **drops `.bss` entirely** from the flat binary -- confirmed empirically (`readelf -l kernel.elf` showed `FileSiz=0x1c0d` vs `MemSiz=0x24e6`; the raw binary came out exactly `0x1c0d` bytes, not `0x24e6`). This means the kernel has only ever "worked" so far because whatever RAM stage2 happened to hand it read as zero for the small amount of `.bss` in use (ring buffers, the IDT table, etc.) -- not because anything actually zeroed it. A large `.bss` array would inherit garbage instead of zeros.
2. Even setting that aside, a 1.2MB static array appended after the kernel's `.data`/`.bss` (loaded at `0x10000`) would push the kernel's memory footprint past `0x90000` -- exactly where `boot/stage2.asm` parks the stack. The backbuffer and the stack would overlap.

**Resolution:** the backbuffer lives at a fixed physical address (`0x200000`, 2MB -- comfortably clear of both the loaded kernel and the stack) accessed via a raw pointer, the same pattern `boot_info.h` already uses for `BOOT_INFO_ADDR` -- not a C array, so it costs the linker nothing and sidesteps the `.bss` question entirely. `gfx_init()` explicitly zeroes it at startup rather than assuming anything about the memory's initial contents. Proper `.bss` zeroing (via linker-provided `__bss_start`/`__bss_end` symbols, zeroed in `kernel_entry.asm` before `kmain`) is still not done -- noted here as a real gap now that it's been identified, deferred since the backbuffer's fixed-address approach doesn't need it to work correctly.

**The architecture:** `gfx_put_pixel`/`gfx_get_pixel`/`gfx_fill_rect`/`gfx_clear` all now read/write the backbuffer -- a plain, hardware-agnostic 32-bit-per-pixel array -- instead of touching video memory directly. This is simpler than before in its own right: the bpp-awareness `gfx_put_pixel` needed since the last bug fix (writing `bpp/8` bytes at the correct stride) moved to the one place that actually needs it, `gfx_present()`, which walks the whole backbuffer and writes it out in whatever format `boot_info->bpp` says the hardware wants. Every other drawing function got simpler by not needing to know hardware format at all.

**Cursor compositing** (`kernel.c`) changed from `erase_cursor()` recomputing the plasma formula to real `save_under_cursor()`/`restore_under_cursor()`: before drawing the cursor somewhere, remember the actual backbuffer pixels there (via the new `gfx_get_pixel`); before moving it, put those exact pixels back. This is correct regardless of what's underneath -- plasma, text, or (later) a window -- because it never has to guess; it just remembers what was really there. `kmain` now builds the whole scene (plasma, title, subtitle, cursor) into the backbuffer and calls `gfx_present()` once per frame (once after the initial draw, once per mouse packet) rather than every draw call being immediately visible.

**Verified in QEMU:** moved the cursor directly over the "O" in "COMPOSITOR" and the ":" in "KERNEL:" (via `mouse_move`), screendumped mid-sweep (cursor visibly sitting on the text), then moved away and screendumped again -- the text renders perfectly intact, no corruption, unlike what the old plasma-recompute approach would have left behind.

**Known tradeoff, not yet addressed:** `gfx_present()` blits the entire 640x480 backbuffer every time, even though only an 8x8 cursor moved -- correct but not efficient. A real compositor would track a damage rectangle (here, just the union of the cursor's old and new position) and only blit that. Deferred until it's an actual observed problem rather than a theoretical one, per not building for hypothetical requirements -- but noted here since window/widget work will make this more relevant, not less.

Files: `kernel/graphics.c`/`.h` (backbuffer, `gfx_init`, `gfx_get_pixel`, `gfx_present`); `kernel/kernel.c` (`save_under_cursor`/`restore_under_cursor` replacing `erase_cursor`, `gfx_present()` calls).

Next up: actual GUI primitives (window/rectangle abstraction, simple widgets, an event loop) can now build on a correct compositing foundation. Proper `.bss` zeroing (flagged above) and damage-rect present are both reasonable to pick up whenever they start actually mattering.

## 2026-08-02 — First GUI primitives: windows, a button, a real event loop

Added `kernel/window.c`/`.h` (a titled rectangle) and `kernel/button.c`/`.h` (a clickable, hoverable rectangle with a label) -- the first actual widgets -- plus a real event loop in `kernel.c` that merges keyboard and mouse input instead of blocking exclusively on one.

**The event loop problem:** `keyboard_read_char()` and `mouse_read_packet()` both worked by blocking (via `hlt`) until their specific device produced something. That's fine for a demo exercising one input at a time, but a real GUI needs to react to *either* input, whichever arrives first, without starving the other. Fixed by splitting each driver into a non-blocking `poll` primitive (`keyboard_poll_char()`, `mouse_poll_packet()` -- return 1 if something was available and already decoded, 0 immediately if not) with the existing blocking function rebuilt on top for callers that still want it. `kmain`'s loop now checks both every iteration, redraws and calls `gfx_present()` if either produced something, and only actually `hlt`s when *neither* did -- the CPU still goes idle between input, just without picking a single device to idle-wait on.

`mouse_poll_packet()` has one small wrinkle: once it finds a valid packet-start byte (bit 3 set), it does briefly `hlt`-wait for that packet's other 2 bytes rather than bailing out non-blockingly -- otherwise, on a partial read, the next `poll_packet()` call would resync onto whatever byte happens to be at the front of the buffer, potentially misreading a second packet's first byte as this one's second. Since all 3 bytes of a real packet arrive back-to-back within the same tight interrupt burst, this wait is negligible in practice, not a real block.

**Window** (`window.c`) is a title bar (filled rect + `text_puts` for the title) plus a body (filled rect) plus a border -- no dragging, no close button, no layering between multiple windows yet, just enough for widgets to live somewhere and to prove the existing drawing primitives compose into something that reads as "a window."

**Button** (`button.c`) is the first widget with actual behavior: `button_hit_test()` (point-in-rect) plus three fill colors (`hovered`, `pressed`, plain) makes cursor position mean something for the first time, rather than just being a shape following mouse input. `kmain` tracks a `prev_left_held` flag to detect the press *edge* (button held this packet, not held last packet, while hovering) rather than counting every packet where the button happens to be down -- otherwise holding the mouse button while sitting still would count as many clicks as packets arrive.

**Demo tying it together:** a "RAVE-OS PANEL" window containing a "CLICK ME" button (hover/press colors, a `CLICKS: N` counter using a small hand-written `format_uint()` -- no libc, no `itoa`), and a live-typed line (`TYPE: ...`, backspace and Enter both handled) fed straight from `keyboard_poll_char()`. `draw_scene()` redraws the entire backbuffer (backdrop, window, button, text, cursor, in that order) every time either input produces an event, rather than tracking incremental per-widget damage -- simpler, and correct by full reconstruction rather than bookkeeping, given the scene stays cheap. Same full-`gfx_present()`-per-frame tradeoff noted in the previous stage; still deferred.

Verified in QEMU: `mouse_move` onto the button showed the hover color; `mouse_button 1` while hovering showed the pressed color and incremented `CLICKS` to 1; `mouse_button 0` returned to hover color without incrementing again; `sendkey h`/`i`/`shift-1` produced `TYPE: HI!` live on screen -- mouse and keyboard events both driving the same redraw loop correctly.

Files: `kernel/window.c`, `kernel/window.h`, `kernel/button.c`, `kernel/button.h` (new); `kernel/keyboard.c`/`.h`, `kernel/mouse.c`/`.h` (poll primitives added, blocking functions rebuilt on top); `kernel/kernel.c` (window/button/event-loop demo); `kernel/Makefile` (`window.o`, `button.o`).

Next up: window dragging (mouse-down on the title bar moves the window) is the natural next step for "actual" windowing, followed by more widget variety (checkboxes, text input fields) and eventually multiple overlapping windows with real z-ordering -- which is also where the deferred damage-rect `gfx_present()` optimization will likely stop being optional.

## 2026-08-02 — An EXIT button, so QEMU's mouse grab doesn't require a force-reboot to escape

Small but overdue fix: there was no way to leave a running Rave-OS session cleanly. QEMU (run via `boot/Makefile`'s `run` target, no special display flags) grabs the host mouse the moment you click into its window, since the PS/2 mouse protocol is relative-motion and QEMU needs exclusive pointer input to generate those deltas. QEMU's own release shortcut (Ctrl+Alt+G) exists for this, but with nothing in the guest OS itself offering a way out, a force-reboot ended up being the escape hatch in practice.

**The real fix is to make the guest exit cleanly, not to rely on remembering a host-side shortcut.** QEMU's default machine type (`pc`, i440fx chipset) emulates a PIIX4 ACPI power-management block; writing `0x2000` to I/O port `0x604` (the PM1a control register) requests an ACPI S5 ("soft off") transition -- the same mechanism a real BIOS/ACPI-aware OS uses to power off hardware, and one of the most common tricks hobby OSes use to shut down cleanly under QEMU without needing any extra `-device`/`-machine` flags. Added `outw()` to `io.h` (alongside the existing `outb`/`inb`) and a `power_shutdown()` helper in `kernel.c` that does exactly this, halting in a loop afterward as a fallback in case the write is ever a no-op on a different machine type.

**Wired up as a second button**, reusing the existing generic `struct button`/`button_draw`/`button_hit_test` from the previous GUI-primitives stage rather than adding any new widget code: an "EXIT" button sits next to "CLICK ME" in the panel, sized to fill the remaining panel width. The event loop's existing hover/press-edge logic (already tracking `prev_left_held` for click-edge detection) extended naturally to a second button by just repeating the same hit-test/edge-detect block against `exit_btn` and calling `power_shutdown()` on its click edge instead of incrementing a counter.

**Verified headlessly**, since the point was confirming an actual mouse click makes QEMU's process exit (not just that the code compiles): booted `disk.img` with `-display none -monitor unix:...`, drove the guest via monitor `mouse_move`/`mouse_button` commands to hover and click the EXIT button, then confirmed the QEMU process itself was gone from `/proc` afterward -- process exit, not a hang or a crash. A `screendump` before the click also confirmed the new button renders correctly alongside the existing panel (border, label, and hover/press coloring all shared with `CLICK ME` for free, being the same widget code).

Files: `kernel/io.h` (`outw`); `kernel/kernel.c` (`power_shutdown()`, `exit_btn`, event loop wiring).

## 2026-08-02 — Erratic real-mouse tracking, and why the EXIT-button test never caught it

The EXIT button worked in headless verification, but booting Rave-OS with a real display and an actual physical mouse showed something new: the cursor didn't track cleanly, it jumped around erratically. This is a genuinely different bug from the earlier "mouse grab has no escape" problem the EXIT button fixed -- and, worse, every prior "verified in QEMU" claim for the mouse driver going back to its introduction had only ever exercised it via the QEMU monitor's `mouse_move`/`mouse_button` commands, which inject synthetic PS/2 packets directly and completely bypass real hardware-grab input. None of that testing ever ran a real, continuous stream of physical mouse packets through the driver.

**Root cause: the event loop couldn't keep up with real input.** `kmain`'s loop redraws the *entire* scene (a per-pixel plasma backdrop, ~307,200 `gfx_put_pixel` calls, plus `gfx_present()` writing the whole 640x480 framebuffer back out one byte at a time through a `volatile` pointer -- up to ~1.2M individual MMIO writes) on **every single mouse packet**. A real mouse streams packets continuously (PS/2 default ~100/sec) -- much faster than that redraw can complete under QEMU's TCG (software) emulation, which this project runs without `-accel kvm`. `mouse.c`'s ring buffer (32 bytes, ~10 packets) backs up during a slow redraw, and `mouse_irq_push_byte()` drops individual *bytes* once full, not whole 3-byte packets -- desyncing the stream's framing. Since `mouse_poll_packet()`'s resync check (bit 3 of byte 0) can coincidentally match a delta byte that happens to land in that position after a drop, it can resync onto garbage mid-packet, decoding nonsense dx/dy values -- exactly the "erratic jumps" observed, and never reproducible via the monitor's synthetic commands because those are sent one at a time, far slower than the redraw loop.

**Fix, in `kernel.c`:** the event loop now drains *every* mouse packet already queued (`while (mouse_poll_packet(...))` instead of `if`) before triggering a single redraw, rather than redrawing per packet. Each packet's position/hover/click-edge state is still applied individually and correctly (so click-edge detection and bounds clamping are unaffected), but a burst of queued packets collapses into one redraw instead of one-per-packet -- keeping the loop caught up with real input instead of falling further behind with every packet that arrives mid-redraw.

**Also fixed in `mouse.c`, found by re-reading the packet format while tracking this down:** byte 0's bits 6/7 (X/Y overflow) were never checked. A real fast mouse flick can exceed the 9-bit signed delta range these packets carry, at which point the device sets these bits to say the reported delta byte is unreliable -- the driver was trusting it anyway. `mouse_poll_packet()` now clamps to the max representable magnitude (255) in the reported direction when either overflow bit is set, rather than trusting a bogus value. This is a real spec-correctness gap, not just defense-in-depth -- fast real mouse motion can trip it even with the redraw fix in place.

**Not changed:** the underlying full-screen-redraw-per-frame architecture (flagged as a deferred tradeoff repeatedly since the backbuffer stage) is still there -- this fix keeps the loop from falling behind by batching redraws, but each individual redraw is exactly as expensive as before. A damage-rect `gfx_present()` remains the real fix for that cost; this stage is now concrete evidence it's worth doing, not just a hypothetical.

**Verified with a real physical mouse** (not just the monitor's synthetic commands, which -- as this whole entry explains -- can't reproduce this class of bug): rebuilt, relaunched with a visible display, moved the mouse around continuously. Cursor tracked smoothly, confirmed by the user directly.

Files: `kernel/kernel.c` (drain-all-queued-packets-before-redraw); `kernel/mouse.c` (overflow-bit clamping).

## 2026-08-02 — Window dragging

The panel window can now be moved by pressing on its title bar and dragging, the natural next step flagged repeatedly since the first-GUI-primitives stage.

**`window_titlebar_hit_test()`** (`window.c`/`.h`) is a point-in-rect test against just the title bar strip, sibling to `button_hit_test()` -- what the event loop checks before starting a drag, so clicking the window body doesn't also grab it.

**Dragging itself needs no grab-offset bookkeeping**, which simplified the implementation: since PS/2 packets are relative deltas rather than absolute positions, applying a packet's raw `dx`/`dy` to the window (and, since they're independent absolute-positioned structs, its child widgets -- `btn`, `exit_btn`) the same way it's already applied to the cursor keeps the cursor's position over the title bar constant for the whole drag, with no separate offset to track. `kmain` tracks one new flag, `dragging_titlebar`: the press that starts a drag (edge-detected the same way button clicks already are) only sets the flag, deferring actual movement to the next packet -- so the initiating click doesn't also apply that same packet's incidental motion. A nice side effect of moving the cursor and the window by the same delta every packet: the cursor's position *relative to* the window never changes during a drag, so it can never drift onto `CLICK ME`/`EXIT` mid-drag and cause a spurious hover or click.

Then confirmed with a real physical mouse, per [[feedback_qemu_input_testing]] -- dragging felt correct interactively, not just in synthetic replay.

## 2026-08-02 — Damage-rect redraw and present

The whole-screen-redraw-per-event cost flagged as a deferred tradeoff since the backbuffer stage -- and named directly as the root cause of the erratic-real-mouse bug two stages ago -- is fixed now: both the backbuffer redraw and `gfx_present()`'s blit to hardware are scoped to a damage rectangle instead of the full 640x480 screen.

**`gfx_present_rect(x, y, w, h)`** (`graphics.c`/`.h`) is `gfx_present()`'s real implementation now, clipped to the screen itself rather than trusting the caller -- `gfx_present()` just calls it with the full screen. Kept the clipping in `gfx_present_rect()` itself (not just at call sites) on the principle that a present function only correct for in-range input is a landmine for whatever uses it next.

**The damage rect** (`kernel.c`, `update_and_present()`) starts as the union of the cursor's old and new position each event -- it moves on nearly every event, so it's always part of the damage. It's then grown to cover the window group (window + both buttons + the CLICKS/TYPE lines, always redrawn as one unit) whenever the window moved, or its hover/press/click/typed state changed, or -- this part matters -- whenever the cursor's own damage happens to *sweep across* the window group without anything about it changing (e.g. the mouse passing over on its way somewhere else). Skipping that last case would silently erase whatever the cursor swept over, since repainting the backdrop underneath it without redrawing what used to be there is exactly the bug the old save/restore-cursor approach existed to avoid, two stages before the whole-screen-redraw approach superseded it. Same logic covers the title/subtitle block as a second always-or-never unit. Each region that ends up damaged is still redrawn as a whole reconstructed unit rather than diffed pixel-by-pixel -- same "correct by full reconstruction" reasoning the old whole-screen redraw used, just scoped down to whatever actually needs it.

**A real bug surfaced while wiring this up, unrelated to damage-rect itself:** window dragging (previous stage) never clamped the window's position -- nothing stopped it from being dragged partially off-screen, at which point `window_draw()`'s `gfx_fill_rect()` calls would write outside the backbuffer entirely (`gfx_put_pixel()` has never bounds-checked). Latent since dragging shipped, just never exercised. Fixed alongside this stage since damage-rect math needs the window's bounds to be sane anyway: dragging now clamps the window's full outer bounds to stay on-screen, and moves the child buttons by the *clamped* delta (not the raw packet delta), so they stay correctly positioned relative to the window even in the frame where clamping kicks in.

**Verified in three passes**, each catching something the previous one wouldn't have: a headless click/hover/type sequence (screendumps matched the pre-damage-rect versions pixel for pixel where content was identical); a deliberately adversarial headless drag -- grabbing the title bar and yanking it hard toward the top-left corner in one giant synthetic delta -- to check the clamp *and* the case where the window's new position ends up overlapping the title text, which it does at the corner; and then, per [[feedback_qemu_input_testing]], a real physical mouse pass (moving, hovering, clicking both buttons, dragging including into the corners, typing) before calling it done, since this is exactly the class of redraw-timing-sensitive change that headless synthetic input can't fully validate. User confirmed: "perfect."

Files: `kernel/graphics.c`/`.h` (`gfx_present_rect()`); `kernel/kernel.c` (`update_and_present()` and its rect-math helpers, drag clamping).

Next up: unchanged -- more widgets, multi-window z-ordering, rounded corners. Multiple overlapping windows will be the next thing to put real pressure on the damage-rect approach (right now there's exactly one window, so "does the window group need redrawing" is a single yes/no; z-ordering will need per-window damage and paint-order to stay correct).

## 2026-08-02 — Multiple windows, z-ordering, and what that does to damage-rect

A second window (`RAVE-OS INFO`, a small static panel with no buttons) joins the panel, positioned to overlap its bottom-right corner from boot so the stacking order means something immediately rather than only after someone drags one on top of the other.

**Exactly two windows, two named identities (`WIN_PANEL`/`WIN_INFO`), not an array.** Same reasoning `btn`/`exit_btn` already used instead of a button array: two fixed, distinct things are simpler as two names than as a generic N-window list with nothing yet to generalize over. If a third window shows up, that's the point to introduce a real list.

**Z-order is one flag:** `panel_on_top` (int, boolean). `topmost_window_at(px, py, panel_on_top, ...)` is the single function everything else builds on -- given a screen point and the current stacking order, it says which window (if either) is actually visible there, checking the front window's bounds first and only falling through to the back one if the front one doesn't cover that point. Hit-testing anything (title bar drag-start, button hover/click) now goes through this first, which is what makes overlap correct: a click on a point where the info window visually covers the panel can only ever hit the info window, never click through to a panel button hidden underneath it.

**Raising a window to front is just: on a press that isn't already dragging something, find the topmost window under the cursor and set `panel_on_top` to match it.** If that same press also landed on that window's title bar, a drag starts too -- so grabbing a background window's title bar both raises and starts moving it in one motion, standard desktop behavior, and it fell out of the hit-testing order for free rather than needing special-casing.

**Damage-rect (previous stage) had to generalize from one region to three: the panel, the info window, and the title block.** The single `window_touched` boolean became per-window `panel_touched`/`info_touched`, plus a new `z_reordered` flag (did `panel_on_top` change this event) that forces *both* windows to redraw, since a stacking swap can change what's visible in their overlap without either one's position or contents changing at all. The bigger structural change: after seeding the damage rect from whatever actually moved/changed, a **fixed-point loop** now checks all three regions against the accumulated damage and pulls in any that overlap but weren't already marked dirty -- repeating until a pass changes nothing (bounded at three regions, so at most three rounds). This is what correctly handles two cases that a single-pass check would miss: the cursor sweeping across a window it didn't otherwise touch (unchanged from the previous stage, just generalized to two windows instead of one), and -- new with overlap -- a window that moved away *revealing* whatever was underneath it, whether that's backdrop or the other window. Skipping this would silently leave stale pixels wherever a window used to be.

**Windows are painted back-to-front in whatever the current stacking order is**, both for the one-time full `draw_scene()` and every damage-rect `update_and_present()` -- redraw order, not just redraw membership, has to follow `panel_on_top` or the wrong window would win in the overlap region regardless of which one actually needed repainting.

**Verified headlessly first**: initial boot screendump confirmed the panel starts on top per the default `panel_on_top = 1`; a click on info's exposed corner raised it correctly (screendump showed it now covering the panel where they overlap); a click back on panel's exposed title bar re-raised it; `CLICK ME` still incremented correctly afterward, confirming the raise round-trip didn't leave hit-testing in a bad state. Then, per [[feedback_qemu_input_testing]], a live pass with a real mouse -- raising each window by clicking it, dragging both around including over each other, confirming the panel's buttons still worked -- before calling it done. User confirmed: "perfect."

Files: `kernel/kernel.c` (`info_panel`, `panel_on_top`, `topmost_window_at()`, `window_outer_contains()`, `clamp_window_to_screen()` factored out of the old inline drag-clamp code, `draw_info_group()`, generalized `draw_scene()`/`update_and_present()`).

Next up: more widgets (checkboxes, text input fields), rounded corners. A third window would be the point to stop hardcoding two named identities and introduce a real window list/array with per-window damage tracked in a loop instead of by hand.

## 2026-08-02 — Text input field with real focus

The panel's old "TYPE:" line accepted every keystroke unconditionally, with nowhere for that to stop making sense once more than one thing on screen could want the keyboard. Replaced it with a real text field widget (`textfield.c`/`.h`, sibling to `button.c`/`.h`): a bounded box that only consumes keystrokes while focused, focused by clicking it.

**No blinking caret.** A blink needs a time source, and there's no PIT timer driver yet -- the whole kernel's only clock right now is however fast interrupts happen to arrive. Rather than fake timing off event counts (which would blink at an arbitrary, hardware-dependent rate, not a real one), the caret is just solid while focused and absent otherwise. Worth revisiting once a real PIT tick exists.

**Focus is one flag on the widget (`focused`), set by the same click-edge logic that already drives button clicks:** in `kmain`'s per-packet button block, `click_edge` (a name introduced here, factored out of the `left_held && !prev_left_held` expression duplicated at each button check before this) now also decides the field's focus every click: hitting the field (and the panel being topmost, same gating buttons already used) focuses it, anything else -- a button, empty panel space, the other window, the backdrop -- defocuses it. This is single-focus-owner behavior for free, without a separate "what currently owns the keyboard" variable: there's only one field, so its own `focused` bit *is* that state.

**`textfield_feed_char()` takes every polled character unconditionally and no-ops if unfocused**, rather than `kmain` checking `tf.focused` itself before feeding -- keeps the focus check in one place (the widget) instead of duplicated at every call site a future second field would add. Backspace and character-append behavior carried over unchanged from the old inline logic in `kmain`; Enter still clears the field (there's nowhere for a field to submit *to* yet, so "clear" is what "\n" meant before this pass too, kept as-is rather than inventing submission semantics nothing asked for).

**Damage-rect tracking** (`update_and_present()`) needed `tf.len` and `tf.focused` added to `panel_touched`'s condition, alongside the existing hover/pressed/click_count checks -- both change what's inside the always-redrawn-as-one-unit panel group without moving the panel itself.

## 2026-08-02 — Rounded corners, and a checkbox widget

Two items off the standing "next up" list.

**Rounded corners** needed a real primitive first: `gfx_fill_rounded_rect_ex()` (`graphics.c`/`.h`), a corner-masked rounded-rect fill with no floats or sqrt -- each of the four RxR corner blocks is tested pixel-by-pixel against the integer circle equation `dx*dx + dy*dy <= r*r`, and the straight edges/middle are still plain `gfx_fill_rect()` calls. A pixel outside the circle in a *rounded* corner is left untouched rather than painted over -- correct because in this damage-rect-based renderer, whatever's underneath (usually a border color laid down first) is always already there, so leaving it alone *is* the rounding. `gfx_fill_rounded_rect()` is the common case (all four corners) built on top.

**The corner mask earns its keep in `window.c`**: a window's outer border rounds all four corners, but the titlebar only rounds its top two and the body only rounds its bottom two. The seam between titlebar and body is an internal line, not part of the window's silhouette -- rounding it too would carve a notch into flat abutting rects for no reason. `button.c` and `textfield.c` just use the plain all-corners helper, since both are single rects with no internal seam.

**Checkbox** (`checkbox.c`/`.h`, new, sibling to `button.c`/`textfield.c`): a toggle box with a label, added to the panel below the text field. Hit-testing covers the box *and* label together (clicking the word "FX" toggles it too, not just the box itself) -- computed as the union of the box's rect and the label's text-height band, same spirit as `button_hit_test()`'s single rect but two source rects unioned. Checked state fills a smaller inset rounded square in the accent color rather than drawing a checkmark glyph -- there's no glyph for one in `font.c`, and a solid inset square reads clearly enough at this size. Wired into the event loop the same way the field's focus click was: computed in the existing `panel_is_topmost`-gated block, toggled on `click_edge`.

**One thing to watch for next time a widget is added to the panel**: both this and the text field's earlier drag bug came from the same root cause -- a new widget's `x`/`y` has to be added to *three* separate places (initial layout math, the panel's drag-apply delta, and `panel_touched`'s damage condition) with nothing enforcing that a new widget actually gets all three. Caught immediately this time by re-checking the drag-apply block specifically because of the text field's bug, but worth being deliberate about next time rather than relying on remembering.

**Verified headlessly**: screendump after boot confirmed rounded corners on both windows (only titlebar-top/body-bottom, seam still flush) and both buttons; the checkbox rendered dim/unchecked with its label; a monitor click on it flipped it to a bright border with the inset accent-colored mark filled in. Real-hardware pass still pending as of this entry.

## 2026-08-02 — Minimize/close titlebar controls, and FX actually does something

Stage two of the SymbOS desktop plan: every window now has SymbOS/Win95-style minimize (`_`) and close (`X`) controls in its titlebar, built directly on the `state` field and hover fields the previous stage's `struct window` generalization added in advance.

**`window.c`** gained `window_minimize_rect()`/`window_close_rect()` (two ~12x12px boxes, right-aligned in the titlebar with small margins/gaps) and matching hit-tests. **`kernel.c`**: a click on a window's controls now short-circuits the existing raise/drag click-edge branch -- close sets `state = WINDOW_CLOSED`, minimize sets `state = WINDOW_MINIMIZED`, both take priority over raising the window (a real desktop doesn't raise-then-close, it just closes). ## 2026-08-02 — Taskbar (implemented, headlessly smoke-tested, paused before live verification)

Stage three of the SymbOS desktop plan: a taskbar strip pinned to the bottom of the screen (new `taskbar.c`/`.h`), one entry per window with `state != WINDOW_CLOSED`, the first way to recover a window hidden by last stage's minimize/close controls.

**Fixed per-index slots, not a packed/reflowing list** -- entry `i` is always window `i`'s slot (`taskbar_entry_rect()`), so a closed window just leaves an empty gap rather than needing the remaining entries to shift over. Same reasoning already used for not building a generic N-window array until it was actually needed: there are only ever `MAX_WINDOWS` possible entries, so indexing beats packing for a fixed small count.

**Click semantics**: the entry for the currently-active window (open and frontmost, `z_order[0]`) minimizes it on click -- a toggle, like clicking a real taskbar button twice. Any other entry (minimized, or open but occluded) restores it to open and raises it to front. ## 2026-08-03 — Desktop icons, closing out the SymbOS desktop plan

Stage four, the last of the four-stage plan: desktop icons (new `desktop_icon.c`/`.h`) for `WINDOW_CLOSED` windows -- the only way to recover a closed window, since the taskbar only lists windows that are open or minimized.

## 2026-08-03 — Stage B: a real interpreter core (immediate execution only)

Stage A's console was a dumb echo terminal; this stage makes it an actual calculator with Forth syntax (real "own dialect" status is Stage C, once colon definitions exist). New `forth.c`/`forth.h`: a tokenizer, a fixed-size 128-cell data stack, and ten primitives (`+ - * / DUP DROP SWAP OVER . CR`). Per the plan, **zero GUI dependencies** -- `forth.c` never includes `graphics.h`, `window.h`, or anything console-shaped; `kernel.c`'s submit branch calls `forth_eval_line(&vm, ci.text, out, sizeof(out))` and splits the `'\n'`-separated result into `console_output_append_line()` calls itself, so the interpreter has no idea a GUI exists at all.

**Two things got real safety attention, not just a mention in the plan** -- this is the first place user-typed input reaches something that can crash the whole machine, not just misbehave locally:

1. **`/` checks for zero before dividing.** `isr.c` has a real vector-0 handler (`isr_divide_error` -> `panic("PANIC: DIVIDE ERROR")`) -- an unchecked `idiv` on this kernel doesn't raise something Forth can catch, it halts the OS. `prim_div()` checks `b == 0` and sets a `DIV BY ZERO` error instead of ever executing the division.
2. **Every stack access is bounds-checked.** `forth_push()`/`forth_pop()` are the only two functions that ever touch `dstack[]`, and both check `dsp` against the array bounds before touching it -- no paging on this kernel, so an unchecked overflow would silently corrupt whatever static data the linker placed next in `.bss`. On any error, `dsp` resets to 0 (real Forth's `ABORT` behavior) rather than leaving a half-consumed stack for the next line.

**A bug caught during headless verification, not in the interpreter logic itself:** the unknown-word error message was originally `"?"` -- invisible, because `font.c` has no glyph for `?` (falls through to its blank-space default, confirmed by grep of `font.c`'s glyph switch). Changed to `"UNKNOWN"`, which only uses characters the font actually renders. A good reminder that this font's character set (confirmed piecemeal across several stages now) is uppercase letters, digits, and a small fixed punctuation set (`: - ! . , ' > %`) -- nothing else renders, silently.

**A real QEMU headless-testing gap, found and root-caused, not worked around silently:** `sendkey equal`, `shift-equal`, `plus`, `slash`, and `shift-8` (asterisk) all produced *nothing* over the monitor socket -- no character reached the keyboard driver at all -- while `minus`, `dot`, digits, letters, and `shift-5` all worked correctly. Checked `/usr/share/qemu/keymaps/en-us` (confirms `equal`/`plus` *are* real QKeyCode names with correct scancode 0x0d), tried `-k en-us` to force that keymap, and tried the same keys over QMP's typed `send-key` command instead of HMP's text `sendkey` -- all failed identically. This is a real gap in this QEMU build's headless `-display none` input path for a specific subset of punctuation keysyms, not a bug in `keyboard.c` (whose scancode table has the correct entries at the right indices, confirmed by direct inspection) or in `forth.c`. Extends [[feedback_qemu_input_testing]]: the known gap was previously about mouse-input timing; this is the same category of gap, now confirmed for a subset of keyboard symbol keys too.

**Verified headlessly** (everything reachable without `+`, `*`, or `/`): `FOOBAR` produced a visible `UNKNOWN` line (confirming the font-glyph fix). `9 4 - .` printed `5` immediately after that error, on the very next line -- proving `ABORT`-style recovery actually works, not just that errors get detected. `DROP` on an empty stack (fresh boot, and again right after the subtraction test popped its own result) correctly produced `STACK EMPTY`, not a hang or garbage. **Live-verified** for everything headless testing couldn't reach, with the user directly confirming each: `3 4 + .` -> `7`, `2 3 * .` -> `6`, `10 2 / .` -> `5`, and critically `5 0 /` produced a `DIV BY ZERO` error with the OS still running normally afterward -- confirming the divide-guard actually fires instead of the CPU's own fault handler. User confirmed: "all worked correctly."

## 2026-08-03 — Stage C: colon definitions, closing out the four-stage Forth plan

`:`/`;` -- the last stage of the plan, and the one that actually earns "Rave-OS's own dialect": the language can now extend itself at runtime by compiling new words out of existing ones, no compiler/linker involved. `forth.h`/`forth.c` gained a real (if simplified) threaded-code interpreter: `struct forth_instr { int op; int32_t arg; }`, a shared append-only `code[]` array (`FORTH_CODE_SIZE = 2048`), a fixed-size dictionary (`FORTH_MAX_WORDS = 64`, name + `code_start`), and a return stack (`FORTH_RSTACK_SIZE = 32`) for nested word calls. A colon definition compiles each token into one instruction: a number becomes `OP_LITERAL`, a primitive name becomes `OP_CALL_PRIMITIVE` (by table index, not re-searched by string), a *previously-defined* user word becomes `OP_CALL_WORD`, `;` becomes `OP_EXIT`.

**One shared execution loop (`forth_exec()`) handles both "run this word typed at the prompt" and "run this word from inside another word's body"** -- an instruction pointer walks `code[]`; `OP_CALL_WORD` pushes the return IP onto `rstack[]` and jumps to the callee; `OP_EXIT` pops back, or returns entirely if `rsp` is back at the depth this particular `forth_exec()` call started at (tracked as `base_rsp`, not just "rsp == 0" -- matters once a word-body call is itself nested inside another `forth_exec()` invocation, though Stage C's forward-reference-only rule means that nesting is currently always exactly one level deep in practice; the depth-relative check is correct regardless). Same code path for both cases, not two separate interpreters -- this was the actual point of designing it as one loop from the start rather than special-casing top-level calls.

**A word can only call words already defined strictly before it** -- `handle_compile_token()`'s dictionary search only looks at `vm->dict[0..dict_len)`, and `dict_len` doesn't grow until a definition completes successfully at `;`. Not a limitation being worked around; real Forth dictionaries have always been a list growing forward in time. This also makes the forward-reference rule enforce itself for free: a word referencing something not yet defined (including itself) simply won't find it and errors with `UNKNOWN`, aborting the whole definition -- no special-casing needed for "you can't call yourself" as a separate rule.

**Same bounds-checking discipline as Stage B's data stack, extended to two more fixed resources**: `forth_emit()` is the one place that ever appends to `code[]`, and checks `code_len` against `FORTH_CODE_SIZE` first (`CODE FULL` error otherwise); `;` checks `dict_len` against `FORTH_MAX_WORDS` before adding the finished definition (`DICT FULL` otherwise); `forth_exec()`'s `OP_CALL_WORD` case checks `rsp` against `FORTH_RSTACK_SIZE` before pushing a return address (`RSTACK FULL` otherwise). On any error mid-compilation, `code_len` is deliberately *not* rewound -- the half-compiled instructions just sit there, inert and unreachable (no dictionary entry ever points at them, since one is only added at a successful `;`), append-only waste rather than a correctness problem to solve.

**Compile-mode state (`compiling`/`awaiting_name`/`compile_name`/`compile_start`) persists across separate `forth_eval_line()` calls**, unlike the transient `out`/`out_pos`/`out_max` output cursor -- deliberately, so a definition can legally span more than one submitted line (hit Enter mid-definition, keep typing the rest on the next line), the same as a real interactive Forth. Nothing extra had to be written for this; it falls out of simply not resetting that state at the top of the function.

**A real, load-bearing headless-testing gap found this stage, not a minor inconvenience:** `sendkey colon` (and `semicolon`) produce *nothing* at all over the monitor socket in this QEMU build -- confirmed by literally typing `: FIVE 5 ;` headlessly and watching the console echo back `FIVE 5` with no `:` characters at all, immediately erroring `UNKNOWN` on `FIVE` (proving the colon press never reached the driver, not that it reached it and got misparsed). Since Stage C's entire feature is unusable without typing `:` and `;`, this isn't a "some primitives untestable" gap like Stage B's `+`/`*`/`/` -- headless verification of this stage's actual behavior wasn't meaningfully possible at all. Every real check this stage got was a live one.

**Live-verified**, all directly confirmed by the user: `: SQUARE DUP * ;` then `5 SQUARE .` -> `25` (proving compilation, dictionary lookup, and nested primitive execution inside a user word all work together). `: NEGATE 0 SWAP - ;` then `7 NEGATE .` -> `-7` (a second word, proving `SWAP`'s stack-order behavior survives being called from inside a compiled body, not just at the prompt). `: A B ;` where `B` isn't defined -- errored `UNKNOWN` as expected, *and* a bare `A` afterward also errored `UNKNOWN` rather than somehow having been registered -- confirming the forward-reference rule and the "no dictionary entry until a definition completes" design both hold. Dictionary/code-space exhaustion (defining `FORTH_MAX_WORDS + 1` words) was **not** interactively tested -- 65 separate colon definitions is impractical to type by hand live, and headless typing of `:` doesn't work at all this session. Confidence in that path rests on code review and the fact that it's the exact same bounds-check pattern already live-verified for the data stack in Stage B, not on having actually exercised it. Worth a real test if this ever becomes suspect.

## 2026-08-06 — Stage D: control flow (IF/ELSE/THEN, BEGIN/UNTIL), and a font gap that made testing itself hard

The Forth plan's own Stage D sketch, picked back up after being paused mid-implementation on 2026-08-03. Two new opcodes in `forth.h`/`forth.c` -- `OP_BRANCH` (unconditional jump) and `OP_BRANCH_IF_ZERO` (pop, jump if the popped value is zero) -- compiled into the same `code[]` array Stage C's word bodies already use. `IF` emits a `OP_BRANCH_IF_ZERO` with a placeholder target and pushes its `code[]` index onto a new compile-time-only `ctrl_stack[]`; `THEN` pops it and patches the target to "here"; `ELSE` patches `IF`'s branch to just past an unconditional jump it emits (for the else-body skip) and pushes *that* jump's index for `THEN` to patch instead. `BEGIN` just remembers the current `code[]` position (no patching needed, nothing branches there yet); `UNTIL` emits a `OP_BRANCH_IF_ZERO` back to it directly, since the loop-back branch doesn't exist until `UNTIL` is reached. Three new comparison primitives (`= < >`) were also needed -- the original Stage D sketch didn't account for `IF` being useless with nothing to branch on -- using real Forth's `-1`/`0` boolean convention (already established as the right call since `OP_BRANCH_IF_ZERO` just tests against zero either way).

**The `ctrl_stack[]` is tagged (`kind`: `CTRL_KIND_IF` or `CTRL_KIND_BEGIN`), not a bare stack of positions** -- so a stray `ELSE`/`UNTIL` or a `BEGIN` closed with `THEN` (wrong pairing, not just "nothing open") errors clearly (`MISMATCHED ELSE`/`MISMATCHED THEN`/`MISMATCHED UNTIL`) instead of silently patching the wrong branch. `;` also now checks `ctrl_sp != 0` (`UNBALANCED CONTROL`) so a definition can't complete with an `IF` never closed by `THEN` -- that would leave a branch instruction permanently pointing at its own placeholder `-1`.

**A real, unplanned detour before any of this could be verified: several characters needed by these exact tests had no font glyph at all.** `font.c`'s glyph switch only ever grew characters piecemeal, one stage at a time, as something happened to get typed -- and this stage was the first to need `;` outside of a colon definition's closing token being *visually confirmed*, plus `< = + * /` for the comparison/arithmetic words in the test cases themselves. All of these fell through to `default: return G_SPACE` (blank), which looks indistinguishable from "the keystroke never registered" -- and did in fact get first misdiagnosed that way live, before checking the font source directly. Added `G_SEMI` (modeled on `G_COLON`'s dot + `G_COMMA`'s tail), `G_LT` (mirrored `G_GT`'s shape), `G_EQ`, `G_PLUS`, and `G_STAR`/`G_SLASH`, all in the same 5x7 dot-grid style as the existing glyphs. Worth noting for future stages: this font's actual coverage has never been fully enumerated in one place, only discovered reactively -- another gap (like Caps Lock being unimplemented, and `(`/`)` still having no glyph) will likely surface the same way next time something new gets typed live.

**A second false alarm during live debugging, not a bug**: a `MAX` definition (`: MAX OVER OVER < IF SWAP THEN DROP ;`) errored `UNKNOWN` on first attempt. Isolated with four narrower tests (bare arithmetic, a plain colon definition with no control flow, bare `<`, and a minimal `IF` with no other primitives in its body) -- all four passed, ruling out a real bug in the new code. The likely cause: `OVER OVER` is the first back-to-back repeated word in any test this project has run live; a single dropped space between two physically identical keypresses would merge them into one unknown token (`OVEROVER`), and would surface exactly where it did -- right after the definition line, before `MAX` is ever called. Retyped deliberately and it worked. Not fixed in code because there's nothing to fix -- this is a keyboard/typing-timing artifact of live QEMU testing, not a kernel or interpreter defect.

**Live-verified**, all directly confirmed by the user: `: MAX OVER OVER < IF SWAP THEN DROP ;` then `3 7 MAX .` / `7 3 MAX .` -> `7` both times (proving `IF`/`THEN`, the comparison primitives, and the branch-patching all work together). `: COUNTDOWN BEGIN DUP . 1 - DUP 0 = UNTIL DROP ;` then `5 COUNTDOWN` -> `5 4 3 2 1` (proving `BEGIN`/`UNTIL`'s loop-back branch and the `=` primitive). `: BAD IF DUP THEN THEN ;` -> `MISMATCHED THEN` as expected, and a bare `BAD` afterward -> `UNKNOWN`, confirming the balance check both fires correctly and prevents a broken word from ever being registered.

## 2026-08-06 — Forth console: command history and Left/Right line editing

Closes the gap explicitly left open at the end of the last entry: Up/Down to recall previously submitted lines, and Left/Right to move an insertion point and fix a typo mid-line, matching normal shell/REPL expectations.

**This needed a real, previously-missing piece of the keyboard driver, not just a console-side change**: PS/2 arrow keys are "extended" scancodes -- an `0xE0` prefix byte followed by the actual code, a 2-byte sequence `keyboard.c` had no concept of at all. Today's `keyboard_poll_char()` reads the ring buffer one byte at a time; a new file-scope `pending_extended` flag (same pattern as the existing `shift_held`) lets it recognize an `0xE0` byte, remember that fact *across calls* if the second byte hasn't arrived yet in the ring buffer, then decode the next byte against just the 4 arrow codes it cares about. Unhandled extended keys (there are many -- Home, End, Delete, numpad Enter, right Ctrl/Alt, ...) are silently drained rather than erroring, same "drop what we don't understand yet" policy the rest of this driver already uses for unmapped plain scancodes. Confirmed zero regression risk before writing anything: an `0xE0`-prefixed sequence's bytes already both failed the existing `code >= SCANCODE_TABLE_LEN` bounds check individually, so arrow keys were a hard no-op before this -- there was no existing behavior to preserve.

Arrow keys surface as 4 new pseudo-characters (`KEY_UP`/`KEY_DOWN`/`KEY_LEFT`/`KEY_RIGHT` in `keyboard.h`, values `0x11`-`0x14` -- unused C0 control codes, chosen the same way `'\b'`/`'\n'` already ride through this same `char`-typed API as sentinels rather than plain text).

**`console_input.c` gained a real cursor** (`ci->cursor`, 0..`len`) -- previously text only ever got appended at the end and backspace only ever removed from the end, with no notion of a position in between. `console_input_feed_char()`'s insert/delete are now cursor-relative (shift the tail of the array left or right by one), but when `cursor == len` -- the case for anyone who never touches the arrow keys -- this is byte-for-byte the same sequence of writes as the old always-at-the-end code, so plain typing is unaffected. Two new entry points: `console_input_move_cursor()` (clamped to `[0, len]`, for Left/Right) and `console_input_set_text()` (bounds-checked overwrite + cursor-to-end, for history recall). The caret in `console_input_draw()` now renders at the cursor's x-position (measured by handing a truncated copy of the text up to `cursor` to the existing `text_width()`, rather than duplicating its per-glyph-advance math) instead of always past the last character.

**New sibling module `console_history.c`/`.h`**, deliberately mirroring `console_output.c`'s existing ring-buffer-with-generation-style design rather than inventing a new pattern: a fixed 16-line ring (`CONSOLE_HISTORY_MAX`, no malloc anywhere in this kernel, same as everywhere else), a `browse_offset` (`-1` = not browsing) tracking how far back the caller has stepped. Knows nothing about GUI/window code -- same "reason about it standalone" discipline as `forth.c`. **A deliberate scope call, not full bash fidelity**: browsing only resets on an actual text edit (typing/backspace), not on Left/Right cursor movement -- so you can move around inside a recalled line and press Up again to keep going further back, but editing a recalled line and then pressing Up starts back over from the most recent entry rather than preserving your edit as its own implicit history slot (which is what real readline does). Simpler to reason about and implement, and good enough for a REPL this size.

**`kernel.c` wiring**: the `ci.focused` branch of the keyboard-feed block now checks for the 4 arrow pseudo-chars first (dispatching to `console_history_prev()`/`_next()` + `console_input_set_text()`, or `console_input_move_cursor()`) before falling through to the existing `console_input_feed_char()` path for everything else. `console_history_push()` is called with the submitted line right before the existing `console_input_clear()` -- has to happen while `ci.text` still holds it. Damage tracking (`touched[WIN_KIND_FORTH]`) previously only compared `ci.len`/`ci.focused`, which misses two new cases this feature introduces: the cursor moving without the text's length changing, and a same-length history recall swapping in different content at the same length. Added an `old_ci_cursor` snapshot (same pattern as the existing `old_ci_len`) and an `old_ci_text[]` snapshot compared with a new small `str_eq()` helper (this kernel has no libc `strcmp`).

**Live-verified**, all directly confirmed by the user: plain typing/submit with the arrow keys never touched still works unchanged (the byte-for-byte-identical-when-`cursor==len` claim above, actually exercised). Up/Up/Down after two submitted lines correctly cycled through them in order. Down pressed with nothing recalled did nothing (no crash, no stray blank submit) -- confirming `console_history_next()`'s `browse_offset < 0` guard. Recalling a line, moving left with the arrow key (caret visibly tracking the cursor, not stuck at the end), inserting a character mid-line, then pressing Enter submitted and evaluated the *edited* line, not the original recalled one.

## 2026-08-11 — Stage A: ATA PIO disk driver, Rave-OS's first disk I/O

The direction picked for this session: a file manager GUI app. That needs a filesystem, which needs disk I/O -- and the kernel had neither. `boot/stage1.asm`/`stage2.asm` read disk via BIOS `int 0x13` in 16-bit real mode to load the kernel itself, but nothing in `kernel/` had ever touched a disk after the switch to 32-bit protected mode, where BIOS disk services no longer exist. Per the user's direction, this is being built as a real on-disk filesystem, not a RAM disk, staged one piece at a time the same way the desktop (4 stages) and Forth (4 stages) were. This entry is **Stage A only**: a polling ATA PIO block driver that can read/write a sector by LBA and prove the round-trip actually persists to disk. No filesystem format, no GUI window yet -- those are later stages.

**A second drive, not extra sectors tacked onto the existing `disk.img`.** A dedicated 1MiB scratch image, `boot/fs.img`, is attached as the primary channel's *slave* (`bus=0,unit=1` in QEMU's `-drive` syntax) alongside the existing boot disk on the *master* (`bus=0,unit=0`, now made explicit in `boot/Makefile`'s `run:` target rather than left to QEMU's default). Same I/O ports as the boot disk (0x1F0-0x1F7 data/control registers, 0x3F6 alternate status/device control) -- just a different bit in the drive/head select register -- so no secondary-channel (0x170-0x177) support is needed yet. Keeps boot-critical sectors and future filesystem sectors from ever being able to collide, and the driver code never needs to know anything about `boot/Makefile`'s kernel-size sector arithmetic. `fs.img`'s Makefile rule has no prerequisites, so `make` only creates it once (zero-filled, via `dd`) and never truncates it again on subsequent builds -- otherwise a previous run's writes would be wiped every time, defeating the entire point of testing persistence.

**Polling PIO, no IRQ14 handler.** Matches the existing `mouse_init()` idiom already in `kmain()`: a synchronous device handshake, safe to run any time (this one specifically runs right after `interrupts_enable()`, since unlike the mouse it isn't racing anything a handler would also touch). `pic_remap()` already masks every IRQ line by default and `interrupts_enable()` only ever unmasks IRQ1/2/12, so IRQ14 needed no code changes at all to stay safely masked.

**`kernel/ata.c`/`.h` (new)**, the driver itself: LBA28 addressing, `ata_read_sector()`/`ata_write_sector()` transferring one 512-byte sector via a 256-word PIO loop (`inw`/`outw` -- `inw` didn't exist in `kernel/io.h` yet; `outb`/`inb`/`outw` did). Two internal polling helpers, `ata_wait_bsy_clear()` and `ata_wait_drq()`, both bounded by a fixed iteration cap (`ATA_TIMEOUT_ITERS`) rather than looping forever -- a real, deliberate departure from `mouse.c`'s unbounded polling loops, justified by a real difference: a PS/2 mouse is always there in this project's QEMU setup, but a missing/misconfigured ATA drive is a real failure mode this driver has to survive rather than hang on. `ata_write_sector()` issues FLUSH CACHE (`0xE7`) after the data transfer, specifically because the entire point of choosing a real disk over a RAM disk is that the write has to actually reach the backing file, not sit in the controller's write cache. A drive-select change is followed by the standard "read the alternate status port 4 times and discard" trick (`ata_delay_400ns()`) -- each read costs ~100ns on real hardware, giving the drive the ~400ns settle time it needs before its status is trustworthy; using the *alternate* status port (0x3F6) rather than the main one (0x1F7) matters too, since reading 0x1F7 can have side effects (clearing a pending interrupt status) that 0x3F6 never does.

**`ata_selftest()`** is the whole of this stage's user-visible surface: detects drive presence (status register reads all-1s -- a floating bus -- when nothing answers), writes a fixed byte pattern to a scratch LBA on the slave drive, reads it back into a second buffer, compares byte-for-byte, and returns one of a handful of static status strings (`"ATA: OK"`, `"ATA: NO DRIVE"`, `"ATA: WRITE FAIL"`, `"ATA: READ FAIL"`, `"ATA: MISMATCH"`). Rather than a new window kind or a one-off framebuffer write that the next frame's redraw would immediately erase, the result is threaded through the *existing* per-frame draw path into the INFO window: `draw_info_group()` (which already draws the ad hoc "DRAG ME TOO" line) gained one more `text_puts()` call, with `ata_status` threaded through `draw_window_by_index()`, `draw_scene()`, and `update_and_present()` the same mechanical way every other per-frame value already flows through that one dispatch point -- no new architecture, just one more parameter passed down an existing chain.

**Verified headlessly**: booted via the existing `-display none -monitor unix:...` harness, and getting a screendump of the INFO window at all turned out to need the same z-order navigation as any other multi-window screendump in this project -- it boots occluded behind the panel. Drove it to the front via monitor `mouse_move`/`mouse_button` commands onto its taskbar tab (not a straight shot: an early `mouse_move 0 90` produced no visible cursor movement at all in the screendump, and only combining a larger horizontal move with a corrective one actually got the cursor to register -- consistent with [[feedback_qemu_input_testing]]'s standing note that synthetic monitor input doesn't always behave like it looks on paper). Once raised, the INFO window showed `DRAG ME TOO` / `ATA: OK`.

**Host-side persistence check** -- the actual point of choosing a real disk over a RAM disk, and not something the in-kernel self-test alone can prove (a write-then-immediate-read-back in the same boot doesn't rule out a value merely surviving in some transient state): after the headless run exited cleanly, `xxd` against `fs.img` directly on the host at byte offset `100 * 512 = 51200` (the self-test's LBA) showed exactly the expected pattern (`00 01 02 03 ... fe ff` repeating twice to fill the 512-byte sector) -- confirmed independent of the kernel process, sitting in the actual file. A second, fresh headless boot against that now-pre-populated sector also completed without incident (the self-test unconditionally rewrites the same pattern every boot regardless of what's already there, so this run was more a "did anything regress" smoke check than an independent persistence proof, but the host-side byte check above is the real one).

**Live-verified**: booted interactively (real QEMU window, both drives attached, same explicit `bus=0,unit=0`/`bus=0,unit=1` invocation as the headless runs), user clicked through to the INFO window, and confirmed on screen: `ATA: OK`.

Files: `kernel/io.h` (`inw()`); `kernel/ata.h`/`.c` (new); `kernel/Makefile` (new object); `kernel/kernel.c` (`#include "ata.h"`, `ata_status` local, `ata_selftest()` call after `interrupts_enable()`, `ata_status` threaded through `draw_info_group()`/`draw_window_by_index()`/`draw_scene()`/`update_and_present()`); `boot/Makefile` (`fs.img` target, `run:` now attaches both drives with explicit `bus`/`unit`).

This closes out Stage A of the (informally staged, not committed further than one stage ahead) path toward a file manager. Next up: Stage B, the filesystem format itself -- sketch only, not a commitment yet, same as every other multi-stage plan in this log: a superblock at a fixed LBA (magic number, block size, file-table location), a flat file table to start (name/start-LBA/size entries, no directory hierarchy yet -- that's its own later stage, same reasoning as Forth's colon-definitions-before-control-flow ordering), and something (host-side tool or a kernel-side format-on-first-boot path) to actually write that superblock before any of it works.

## 2026-08-11 — Stage B: filesystem format, Rave-OS's first real files

Picked up the Stage A sketch immediately: a superblock, a flat file table, and named create/read on top of last entry's ATA driver. Still no GUI -- the file manager waits until there's a real filesystem to browse.

**Layout on `fs.img`** (2048 sectors at 512 bytes each -- a fact `kernel/fs.c` and `boot/Makefile`'s `dd ... count=1` now both have to agree on, the same kind of cross-file constant this project has hit before with disk-sector layout, and equally undetectable by the compiler if the two ever drift apart): LBA 0 is the superblock (magic, version, total sector count, a `next_free_lba` bump-allocator cursor); LBA 1 is the file table, a fixed array of 20 `struct fs_file_entry { char name[16]; uint32_t start_lba; uint32_t size_bytes; }` (24 bytes each, 480 of the sector's 512 bytes used); LBA 2 onward is file data, handed out contiguously by the bump allocator. The magic number is deliberately the 4 ASCII bytes `"RAVE"` packed into a little-endian `uint32_t` (`0x45564152`) specifically so it reads as literal text in a hex dump, the same reasoning that shaped `ata_selftest()`'s pattern choice last entry.

**`name[0] == 0` marks a free file-table slot** -- no separate valid/used flag, the same "let the data encode its own emptiness" approach `forth.c`'s dictionary already uses for its own entries. **Write-once**: `fs_create_file()` fails outright if the name already exists; no delete, overwrite, or space reclamation yet, deferred on purpose rather than half-built now.

**A real conflict Stage A's design left behind, caught before it could cause silent corruption**: `ata_selftest()`'s scratch write lived at LBA 100, chosen back when the whole disk was undifferentiated scratch space. Once Stage B's allocator can legally hand out any LBA from 2 onward to a real file, LBA 100 was no longer safe -- a file landing there would get silently overwritten by the diagnostic on every subsequent boot, with no error, just quietly wrong data. Fixed by permanently reserving the disk's *last* sector (LBA 2047) for the self-test instead, and capping the allocator's ceiling at `FS_TOTAL_SECTORS - FS_RESERVED_TAIL_SECTORS` so it can never reach it. Caught during planning, not debugging -- worth noting as a real example of why the plan step that lists exactly what a new stage touches on disk is doing its job.

**Mount-or-format happens automatically in `fs_init()`**: read LBA 0, and if the magic doesn't match, write a fresh superblock and a zeroed file table right there -- no separate host-side `mkfs` tool needed, a blank `fs.img` just works the first time anything calls in.

**`fs_selftest()` produces its cross-reboot persistence proof almost for free, as a direct consequence of the write-once design**, rather than needing separate machinery for it: it calls `fs_init()`, then tries `fs_read_file()` on a fixed test filename (`SELFTEST.TXT`, content `"RAVE-OS FS OK"`) *first*. Found and matching -- the case on every boot after the very first -- means the comparison it just did **is** the proof that a real named file, not just a raw sector, survived an entire reboot. Not found (first boot on a fresh image) falls through to create-then-read-back-and-compare, the same shape as `ata_selftest()`'s own check. One of a handful of status strings either way (`"FS: OK"`, `"FS: WRITE FAIL"`, `"FS: READ FAIL"`, `"FS: MISMATCH"`), surfaced the identical way `ata_status` was last entry: a third `text_puts()` line in `draw_info_group()`, `fs_status` threaded through `draw_window_by_index()`/`draw_scene()`/`update_and_present()` alongside it -- one more parameter down the same existing chain, no new plumbing.

**Verified headlessly** on a freshly zeroed `fs.img`: raised the INFO window the same way as last entry (monitor `mouse_move`/`mouse_button` onto its taskbar tab -- this time the working sequence needed each move issued as its own separate monitor round-trip with a beat in between rather than batched together, a batch of four `mouse_move`s plus a click sent in one shot produced no visible cursor movement at all, another small confirmation of [[feedback_qemu_input_testing]]'s standing note), and the INFO window showed `DRAG ME TOO` / `ATA: OK` / `FS: OK`.

**Host-side structural check**, same rigor as Stage A's: after that run exited, `xxd` against `fs.img` on the host showed exactly what was expected at every layer -- LBA 0 opens with `5241 5645` (`RAVE`), version `1`, total sectors `0x800` (2048), `next_free_lba` `3`; LBA 1's first entry reads `SELFTEST.TXT` in plain ASCII with `start_lba = 2`, `size_bytes = 13`; LBA 2 holds the literal bytes of `"RAVE-OS FS OK"`. All independent of the kernel process, sitting in the file itself.

**Reboot check**: a second headless boot against that same now-formatted image showed `ATA: OK` / `FS: OK` again -- this time necessarily via `fs_selftest()`'s "found it, compare" path rather than "create it," since the file already existed. This is the actual proof a named file survives a real reboot, not the weaker smoke-check Stage A's raw-sector persistence check could offer.

**Live-verified**: booted a third time, fully interactively, user clicked through to the INFO window and confirmed `FS: OK` on screen.

Files: `kernel/fs.h`/`.c` (new); `kernel/ata.c` (`ATA_SELFTEST_LBA` moved from `100` to `2047`); `kernel/Makefile` (new object); `kernel/kernel.c` (`#include "fs.h"`, `fs_status` local, `fs_selftest()` call after `ata_selftest()`, `fs_status` threaded through the same four functions `ata_status` was).

This closes out Stage B. Rave-OS can now create and read real named files that survive a reboot, on top of the raw sector access Stage A proved. Next up: not yet decided beyond the informal one-stage-ahead sketch. The obvious next increment if this thread continues is directory hierarchy (a real path structure instead of one flat namespace) and/or the file manager GUI itself finally becoming buildable on top of this -- but per this log's standing practice, that's a call for whenever that stage actually starts, not a commitment made now.

## 2026-08-11 — Stage C: directory hierarchy, a real path structure

Given the choice between directory hierarchy and jumping straight to the file manager GUI, the call was hierarchy first -- meaning the GUI waits one more stage, but it also never has to be rebuilt around directories arriving after it.

**Every directory, root included, is the same shape Stage B's single flat table already was**: one 512-byte sector, up to 20 entries. A subdirectory is just *another* one of those tables, allocated from the exact same bump allocator that already handed out file data sectors -- no separate directory-sector pool, no new allocation concept. `struct fs_file_entry` (renamed `struct fs_entry`, since it's no longer only files) gained a `uint8_t type` (`FS_TYPE_FILE`/`FS_TYPE_DIR`); for a directory entry, `start_lba` points at that subdirectory's own table sector instead of file data. 25 bytes/entry now (was 24) -- still comfortably 20 entries in one sector.

**This changes the on-disk layout, so `FS_VERSION` bumped to 2, and `fs_init()`'s existing mount-or-format check gained a version comparison alongside the magic check.** Worth spelling out why magic alone wasn't enough: an old Stage B image's magic bytes are still perfectly valid `"RAVE"` -- only the *layout behind* them changed, which magic bytes can't detect on their own. This is the same mount-or-format mechanism Stage B already built, just taught a second trigger condition, not new machinery. Concretely this meant Stage B's on-disk `SELFTEST.TXT` was destined to get wiped and reformatted the moment Stage C's kernel booted against it -- flagged plainly in the plan rather than discovered mid-test, and confirmed exactly as expected: booting Stage C's kernel against the *unmodified* Stage B `fs.img` (superblock still reading version `1` going in) came back out reading version `2`, a fresh root table, and a newly created nested test file, all in the one boot.

**Paths are absolute and `/`-separated** (`/TESTDIR/NESTED.TXT`) -- no relative paths or a current-directory concept, since nothing in this kernel has a "current directory" to be relative to yet. `path_split()` is a small hand-written splitter (no `strtok` in this freestanding, libc-less kernel -- same reasoning as `forth.c` writing its own tokenizer rather than reaching for one), capping components at 15 characters and paths at `FS_MAX_PATH_DEPTH` (4) components. The one genuinely new piece of logic this stage adds is `walk_to_parent()`: starting from the root table, it follows each directory component's `start_lba` into the next table, and hands back the LBA of whichever table should hold the final path component plus that component's own name. Everything underneath it -- `dirtable_read`/`dirtable_write`/`dirtable_find`/`dirtable_find_free` (renamed from Stage B's `ft_*` now that "the file table" is no longer singular) -- is Stage B's own per-table logic, just generalized to take an LBA argument instead of a hardcoded one.

**`fs_create_file()`/`fs_read_file()` keep their exact Stage B signatures** -- a caller passes a path, full stop, with no special-casing for "is this nested or not." New: `fs_create_dir()`, same write-once/parent-must-exist shape as file creation, allocating one fresh zeroed table sector and adding a `FS_TYPE_DIR` entry for it in the parent's table. A small `alloc_sectors()` helper now backs both -- factored out of what was file-creation-only logic in Stage B, since directory-table allocation needed the identical reserved-tail-boundary check. It commits the bump allocator's new position to disk immediately on success, before the caller's own entry gets written -- meaning a failure partway through writing a multi-sector file after allocation succeeds leaks those sectors (nothing will ever point at them) rather than rolling the allocation back. Deliberately not handled: same "leak, don't corrupt" tolerance this project has already accepted elsewhere (Forth's Stage C leaves half-compiled instructions inert and unreachable in `code[]` on a failed definition, for the identical reason -- rollback machinery is real complexity a rare failure path doesn't earn yet).

**`fs_selftest()` moved from a root-level file to `/TESTDIR/NESTED.TXT`** -- strictly more coverage than Stage B's check, since resolving that path exercises the directory-walk logic (finding `TESTDIR` in the root table) *and* file creation inside a subdirectory in the same pass, with the "read first, create only if not found" trick still doing double duty as the cross-reboot persistence proof, now for a nested structure instead of a flat one. New status string `"FS: MKDIR FAIL"` alongside the existing `"FS: WRITE FAIL"`/`"FS: READ FAIL"`/`"FS: MISMATCH"`.

**No `kernel.c` or UI changes this stage** -- `fs_selftest()`'s return contract never changed shape, so the INFO window's existing `FS: ...` line kept working with zero edits. Entirely self-contained inside `kernel/fs.c`/`fs.h` (plus `kernel/ata.c`'s reserved-sector comment, unchanged in substance).

**Verified headlessly** against the *actual* Stage B `fs.img` left over from the last entry, specifically to prove the version-mismatch reformat path fires rather than being taken on faith: raised the INFO window (same one-monitor-command-per-round-trip timing as the last two stages), screendump showed `FS: OK`.

**Host-side structural check**, deeper than either previous stage's since there's now a real tree to walk: `xxd` on the root table (LBA 1) showed a `TESTDIR` entry with `start_lba = 2` and the type byte set to `01` (`FS_TYPE_DIR`); `xxd` on LBA 2 (the LBA the root entry pointed at) showed a `NESTED.TXT` entry with `start_lba = 3`, `size_bytes = 13`, type byte `00` (`FS_TYPE_FILE`); `xxd` on LBA 3 showed the literal bytes of `"RAVE-OS FS OK"`. Every link in the chain checked independently against the file on the host, not taken on `fs_read_file()`'s word for it.

**Reboot check**: a second headless boot against that same now-Stage-C-formatted image showed `FS: OK` again, this time necessarily via the "found it, compare" path -- the real proof a nested directory and the file inside it both survive a full reboot, not just get recreated identically every time.

**Live-verified**: booted a third time, fully interactively, user clicked through to the INFO window and confirmed `FS: OK` on screen.

Files: `kernel/fs.h` (path-syntax doc comments, `fs_create_dir()` declaration); `kernel/fs.c` (`struct fs_entry` with `type`; `FS_VERSION` 2; `FS_ROOT_LBA`; `path_split()`/`walk_to_parent()`/`alloc_sectors()` new; `dirtable_*` renamed with an LBA parameter; `fs_init()`'s version check; `fs_create_dir()` new; `fs_create_file()`/`fs_read_file()` routed through `walk_to_parent()`; `fs_selftest()` targeting `/TESTDIR/NESTED.TXT`).

This closes out Stage C. Rave-OS's filesystem now has real nested directories, not just one flat namespace. ## 2026-08-11 — File manager, Stage A: a 4th window that lists the root directory

The obvious next increment, picked up immediately: a window that can actually see the tree Stage C proved exists. Following this project's own standing rhythm -- every prior multi-part feature started with the narrowest possible slice, the desktop's window-list generalization before minimize/close/taskbar/icons, Forth's echo terminal before any interpreter -- this stage is **read-only listing of the root directory only**: no navigating into subdirectories, no create/rename/delete UI yet.

**`kernel/fs.c` had no way to list a directory's contents from outside itself** -- every existing call (`fs_create_dir`/`fs_create_file`/`fs_read_file`) requires already knowing an exact path. New public `fs_list_dir(path, out, max_entries, *out_count)`, returning `struct fs_dirent { name; type; size_bytes }` per entry. `FS_MAX_FILES`/`FS_NAME_MAX` (previously private to `fs.c`) moved into `fs.h` alongside it -- now a real public contract, since any caller sizing a listing buffer needs to know them, not just an implementation detail.

**One new piece of walking logic, `resolve_dir_lba()`, plus a shared `walk_components()` factored out of `walk_to_parent()`.** `walk_to_parent()` (used by file creation/reads) needs to stop *one component short* -- it hands back the parent table plus the leaf name for the caller to look up or insert. `resolve_dir_lba()` (new, for listing) needs to walk *every* component, since it's resolving the directory itself, not something inside it -- and `"/"` is a fixed special case, since root has no parent to look itself up in. Rather than duplicate the walking loop with one boundary changed, `walk_components(components, n, *table_lba)` takes the count as a parameter, and both callers just pass a different `n`.

**A 4th window kind, `WIN_KIND_FILES`** (`MAX_WINDOWS` 3 -> 4). This is the first time a window kind has been added since the desktop's original 3-window design, and it confirmed something worth knowing for next time: every generic window mechanic -- `taskbar_draw()`, `desktop_icons_draw()`, `topmost_window_at()`, drag/raise/minimize/close, all the damage-tracking loops -- already took `MAX_WINDOWS`/`count` as a parameter rather than hardcoding 3, specifically because the desktop stages were built that way on purpose. Bumping one constant gave the new window a taskbar tab, a desktop icon slot, dragging, minimize/close, and z-order entirely for free. Only two hand-written per-kind spots needed a new branch at all: `draw_window_by_index()` (a new `draw_files_group()` case) and `move_window_content()` (a no-op branch, same as `WIN_KIND_INFO`'s -- nothing draggable in a read-only listing).

**The listing is read once at boot, not on every redraw** -- `kmain()` already computes `ata_status`/`fs_status` once and threads them through the draw functions as plain parameters; `file_entries[FS_MAX_FILES]`/`file_entry_count` are computed the identical way, one `fs_list_dir("/", ...)` call right alongside the other two self-tests. This kernel's event loop redraws on essentially any mouse movement, not a fixed frame rate -- re-reading the directory sector that often would mean a PIO polling round-trip on nearly every frame once this window existed, the same reasoning that already justified computing `ata_status`/`fs_status` once rather than per-frame.

**`draw_files_group()`** draws window chrome, then one `text_puts()` line per entry -- directories suffixed `/`, files shown with their size in bytes via the existing `format_uint()` helper (already used by the panel's `CLICKS:` counter), `"(EMPTY)"` if the directory has nothing in it. Sized for ~8 visible lines, comfortably more than the current tree needs; scrolling past that is a real gap, deliberately not solved before there's enough real content to hit it.

## 2026-08-12 — File manager, Stage D: delete

Picked up as the first slice of "create/rename/delete UI" -- deliberately narrowed to just delete, chosen because it needs neither a new text-entry widget (create/rename both will) nor a rename-specific op, just a way to pick a row and a button to act on it. Still no creating or renaming anything.

**`fs_delete()` is genuinely new to `fs.c`** -- every prior write path (`fs_create_dir`/`fs_create_file`) was explicitly write-once/no-delete ("deferred to a later stage," per Stage B of the filesystem work). ## 2026-08-14 — File manager, Stage F: rename, closing out the staged file manager plan

**`fs_rename(path, new_name)` is new in `fs.c`/`fs.h`** -- the first filesystem mutation since Stage C's directory hierarchy that isn't create or delete. Deliberately narrow: `new_name` is a bare leaf, not a path, so this can only rename an entry in place within its existing parent directory, never move it elsewhere -- a real move (reparenting across directories) is a different, harder operation (updating two directory tables instead of one) that nothing in the GUI asks for yet, so it wasn't built speculatively. Implementation mirrors `fs_delete()`'s shape: `walk_to_parent()` to find the entry's table and slot, then three checks before touching disk -- the entry must exist, `new_name` must be a legal single component (non-empty, no `/`, at most 15 characters, the same bound `path_split()` enforces per-component), and no *other* slot in the same table may already have that name (renaming to your own current name is allowed, treated as a harmless no-op write). On success, `name_copy()` overwrites just the `name` field in place -- `start_lba`/`size_bytes`/`type` are untouched, and critically, the entry keeps the same table slot, so a caller's listing index for it doesn't change.

**GUI change, no new button.** The original Stage E note flagged rename as needing to combine that stage's name field with Stage D's row selection -- but a fourth button (RENAME, alongside NEW DIR/DELETE) has nowhere to go in a 180px-wide footer already at two buttons. Instead, Enter's meaning in `name_input` now branches on `files_selected`: with a row selected (Stage D's right-click selection), Enter renames that entry to the typed name via `fs_rename()`; with nothing selected, Enter creates a plain file, exactly as Stage E left it. This is the same "split the action, don't duplicate the field" reasoning Stage E used for NEW DIR vs. plain Enter, just applied one level up -- selection state disambiguates which of two meanings Enter has, rather than a new widget. Failure (not found, name taken, too long, empty) is the same silent no-op as every other FILES-window failure so far: the typed text stays in the field so the user can see and fix it. A successful rename deliberately leaves `files_selected` unchanged rather than clearing it (unlike a successful delete) -- since the rename is in-place and the slot index is stable, the same row is still valid and now shows the new name, still highlighted, which reads as direct confirmation the rename took.

**Verified headlessly**, same disposable-scratch-copy-of-`fs.img` discipline as Stages D/E: right-clicked `TESTDIR/` to select it, typed `RENAMED`, pressed Enter -- the row became `RENAMED/`, still highlighted, name field cleared. Deselected, typed `HELLO2`, pressed Enter with nothing selected -- confirmed plain create is untouched by the new branch. Selected `HELLO2`, typed `RENAMED` (the name just given to the other entry) and pressed Enter -- confirmed the collision guard rejects it: listing unchanged, `HELLO2` still selected, `RENAMED` left sitting in the field rather than silently eaten. All three cases match the design intent exactly.

**A `mouse_move`/`sendkey` timing note, distinct from the ones already on record:** the monitor's `mouse_move dx dy` command didn't reliably apply a large single delta in one call during this pass (e.g. requesting `522 468` from a corner landed closer to `425 370`) -- chunking large moves into several sub-127 steps with a short delay between each got the cursor to the intended pixel reliably, then a final small corrective delta closed the gap exactly. Files: `kernel/fs.h`/`.c` (`fs_rename()`, new); `kernel/kernel.c` (header comment; the `name_input.focused` Enter-key branch in the keyboard block now checks `files_selected` and calls `fs_rename()` or `fs_create_file()` accordingly).

## 2026-08-15 -- Forth `@`/`!` memory access, closing the last deferred gap in the Forth dialect

Picked up as the "next direction" after the file manager's staged plan closed out -- the smaller of the two open candidates (this, vs. Stage 4 self-hosting), chosen because it directly finishes the Forth dialect's own deferred list rather than starting a much larger new effort.

**Deliberately not raw address access into kernel RAM.** Real Forth's `@`/`!` touch actual memory, but this kernel has no paging or memory protection at all -- a user-typed `9999999 !` would silently corrupt whatever `.bss` the linker happened to place nearby, exactly the class of bug `forth.c`'s own header comment warns the whole file is designed to prevent. Instead, `@`/`!` address a new dedicated scratch array, `int32_t mem[FORTH_MEM_SIZE]` (`FORTH_MEM_SIZE` 64) on `struct forth_vm` -- cell-indexed (0..63, matching the data stack's own `int32_t` width, not byte-offset), bounds-checked exactly like every other array access in this file. An out-of-range address is a Forth-level `BAD ADDR` error, never memory corruption. `forth_init()` doesn't explicitly zero `mem[]`, following the exact precedent already set by `dstack[]`/`code[]` -- neither is zeroed per-call either, relying on `.bss` zero-init at boot and staying that way.

**Two new primitives, same shape as every other one in `primitives[]`**: `prim_fetch` (`@`, `addr -- value`) pops `addr`, bounds-checks, pushes `mem[addr]`. `prim_store` (`!`, `value addr -- `) pops `addr` then `value` (stack order: `addr` was pushed last, so it's popped first, same convention `prim_sub`/`prim_div` already use for their operand order), bounds-checks, writes `mem[addr] = value`. No `fs.c` or `kernel.c` changes at all -- this is entirely inside `forth.c`/`forth.h`, continuing the same "no GUI dependencies" isolation the file's header comment establishes.

**A real font gap, caught before it could cause a live-testing false alarm**: `font.c` had a glyph for `!` (added back in Stage D's control-flow work) but none for `@` -- it would have rendered as blank space, indistinguishable from a dropped keystroke, the same class of bug that already bit `;`/`<`/`=`/`+`/`*`/`/` in earlier stages. Added `G_AT` and wired it into `font_glyph()`'s switch before this stage's live pass, not after hitting it.

**A new, now-confirmed headless-testing gap, same category as `:`/`;`/`equal`/`plus`/`slash`/`shift-8`**: `sendkey exclam` and `sendkey at` (QEMU's key names for `!` and `@`, both shift-modified per `/usr/share/qemu/keymaps/en-us`) produced *nothing* over the HMP monitor socket -- confirmed by typing `5 3 !` headlessly and watching the input field stop at `5 3 ` with no `!` ever appearing, then clearing it with backspace (which *did* work) and confirming `@` alone produced the same nothing. Since this stage's entire feature is unusable without typing `@`/`!`, headless verification of the actual behavior wasn't possible at all here, same situation Stage C hit with `:`/`;` -- every real check this stage got was a live one.

**Live-verified**: user typed `5 3 !` then `3 @ .` -> `5` (store/fetch round-trip through the new scratch array), then `999 @ .` -> `BAD ADDR` with the OS still running normally afterward, confirming the bounds check actually fires rather than reading out of the array. User confirmed: "works."

Files: `kernel/forth.h` (`FORTH_MEM_SIZE`, `mem[]` field); `kernel/forth.c` (`prim_fetch`, `prim_store`, both added to `primitives[]`); `kernel/font.c` (`G_AT` glyph, wired into `font_glyph()`).

This closes out the Forth dialect's last deliberately-deferred gap (arithmetic, stack ops, user-defined words, control flow, command history, and now memory access are all done). Next direction is an open call again -- Stage 4 (self-hosting) is the only item left on the original 4-stage roadmap, per this log's standing practice of not committing to it until it actually starts.

## 2026-08-15 -- Unix-like system folders for the file manager

Picked up next: the file manager's persistent `fs.img` root only ever showed whatever a user (or a test session) had created by hand -- a mix of ad-hoc test directories with nothing resembling a real filesystem layout. Planned via superpowers brainstorming (design spec at `docs/superpowers/specs/2026-08-15-unix-like-system-folders-design.md`) and executed via superpowers subagent-driven development against a written plan (`docs/superpowers/plans/2026-08-15-unix-like-system-folders.md`), two tasks, each independently reviewed clean.

**Two tiers, because this kernel only has real live state to expose for exactly one of the seven folders.** `/BIN /ETC /HOME /USR /VAR /TMP` are plain real directories -- genuinely persisted, genuinely empty, since nothing in this kernel yet generates real content for them (no process loader, no config subsystem, no logging). `/DEV` is different in kind: fully synthetic, never written to disk at all.

**Task 1: `fs_bootstrap_dirs()`** (`kernel/fs.h`/`fs.c`), a new function that loops the existing `fs_create_dir()` over the six standard names, discarding the `-1` ("already exists", or a full parent table) return the same way `fs_selftest()` already does for `/TESTDIR` -- idempotent, safe to call every boot rather than only on a fresh format, so it works immediately against the persistent `fs.img` without a reformat. Called once from `kmain()`, right after `fs_status = fs_selftest();`, so the directories are present in the very first rendered frame. Deliberately excludes `/DEV`, reserved for Task 2. Verified headlessly: booted, raised the FILES window via its taskbar tab, screendump confirmed `BIN/ ETC/ HOME/ USR/ VAR/ TMP/` all present in the root listing alongside pre-existing test clutter (left untouched, out of scope). Committed `888ad87`.

**Task 2: `/DEV`, fully synthetic, plus three write-guards protecting the reserved name.** `fs_list_dir("/DEV")` short-circuits before any real dirtable resolution, calling a new static `fs_list_dev()` instead: `HDA` is always listed (this kernel boots from the ATA master, so it's present by construction whenever code is running to ask -- no probe needed), `HDB` is listed only if a live read of the filesystem superblock sector succeeds *right now*, reusing the exact check `fs_init()` already trusts to mount rather than inventing new per-drive ATA-protocol presence detection (this kernel's ATA layer has never been tested against anything but QEMU's always-present backing files, so real per-drive detection semantics were judged not worth the risk for a first cut). Three guards, all case-sensitive exact-match against `"DEV"` (matching this file's existing case-sensitive convention throughout, not introducing a new comparison style) -- `fs_create_dir()`/`fs_create_file()` refuse the name at root, `fs_rename()` refuses renaming something to it at root. Nothing else needed guarding: creating inside `/DEV` and deleting `/DEV` itself both already fail for free through existing path-walking and dirtable-lookup logic, since `/DEV` is never actually on disk to find.

**Two real gaps found in this stage's own testing recipe while executing Task 2, neither a code defect:** the plan's headless test steps assumed `sendkey d`/`e`/`v` (unshifted) would type the reserved uppercase name `DEV` -- it doesn't, `keyboard.c`'s scancode table makes unshifted letter keys lowercase, so the first attempt created a real, harmless lowercase `dev` directory (exactly the case-sensitive behavior the guard is specified to allow, not a bug) before being corrected to `shift-d`/`shift-e`/`shift-v` and deleted. Both tasks passed independent task review with zero Critical/Important findings (Task 1 had one Minor, a doc-comment forward-reference that Task 2 resolved as planned). Rave-OS's file manager now shows a recognizable Unix-like root from boot -- though it's scaffolding, not a populated system: `/BIN`/`/ETC`/`/HOME`/`/USR`/`/VAR`/`/TMP` are real but empty (nothing in this kernel yet produces content for them), and `/DEV` reflects genuine live hardware presence but not real device I/O.

## 2026-08-15 -- RUN: loading and executing Forth scripts from disk

Picked up next, after the user asked for /BIN/etc. to hold "functional" content rather than just empty scaffolding. Decomposed first: a real machine-code loader for `/BIN` is a huge, separate undertaking (no paging, no process isolation, no binary format defined) -- the tractable slice is that Rave-OS already has its own Forth interpreter, so `/BIN` can hold *Forth scripts* instead, with a console command that reads and runs one.

**`RUN <name>`, typed at the Forth console, is a console-level convenience, not a real Forth word.** Deliberately implemented entirely in `kernel.c` rather than `forth.c` -- `forth.c`'s header comment has said since Stage A that it should be reasoned about with zero GUI/filesystem dependencies, and RUN doesn't need to change that: it's intercepted in the Enter-key handler *before* `forth_eval_line()` is ever called, the same way a shell's `source` command isn't part of the language it loads. This also sidesteps a real limitation: a Forth primitive taking a string argument doesn't fit this dialect's pure-int32-stack model at all without inventing string literals/memory first, a bigger feature nothing currently asks for.

**Path resolution**: a bare name (`RUN HELLO`) resolves against `/BIN` (`/BIN/HELLO`), giving that directory real purpose; a leading `/` (`RUN /HOME/FOO`) is used as-is for a script living elsewhere. Deliberate, not just convenient: `sendkey slash` is one of this project's confirmed-broken headless keys, so the common case needs no `/` at all and stays headlessly testable -- only the absolute-path form would be live-only.

**Execution**: reads the file (`VIEWER_BUF_SIZE`, the same 512-byte convention the viewer already uses), splits it on `\n`, and calls `forth_eval_line()` once per line -- exactly as if each line had been typed and Entered individually. This means a multi-line colon definition inside a script works for nothing extra: `compiling`/`awaiting_name` already persist across separate `forth_eval_line()` calls (see the Stage C note in forth.h), so a script's `:`...`;` spanning two lines compiles correctly across two separate calls the same way typing it interactively across two Enters already did. Guarded to only intercept `RUN` when the VM isn't already mid-definition (`!vm.compiling`), so a stray `RUN` token typed inside a `:`/`;` body falls through to the compiler instead of being hijacked -- it just errors `UNKNOWN`, same as any other undefined word would.

**A real gap surfaced before writing any code, not after**: there's no in-OS way to author a multi-line text file yet -- the file manager can only create empty (0-byte) files, and there's no text editor. RUN would have nothing to run without it. Resolved by seeding one real demo script, `/BIN/HELLO` (`: GREET 42 . CR ;` then `GREET`), at boot -- the exact same pattern `fs_selftest()` already uses for its own `NESTED.TXT`, and equally idempotent (`fs_create_file()`'s write-once `-1` on repeat boots is silently ignored).

**A DRY cleanup fell out of this naturally**: the '\n'-splitting loop that turns a buffer into console lines already existed twice (the viewer's file-read output, and the Forth console's `forth_eval_line()` output) before RUN needed it a third time for its own per-script-line output -- three near-identical inline loops was past the point this project's own duplication tolerance holds elsewhere, so it's now one shared `append_split_lines()` helper, with all three call sites (including the two pre-existing ones) switched over.

**Verified headlessly**, with one real testing mistake along the way, not a code bug: the first attempt typed `RUN HELLO` using unshifted `sendkey h/e/l/l/o`, which types lowercase per `keyboard.c`'s scancode table -- producing `/BIN/hello`, which genuinely doesn't exist (`fs.c` is deliberately case-sensitive, same as the `/DEV` guards), so `RUN FAILED` was the *correct* result for that exact input, not a defect. Confirmed `/BIN/HELLO` really was on disk and really was 24 bytes via the FILES window before re-typing with `shift-h/e/l/l/o` for genuine uppercase -- `RUN HELLO` then correctly printed `42`, proving the colon-definition-across-a-script-line-split behavior end to end. Regression-checked plain Forth evaluation (`34 .` -> `34`) still works unchanged after the `append_split_lines()` refactor.

Files: `kernel/kernel.c` only -- `append_split_lines()` new (replacing two inline loops); `match_run_command()`/`forth_run_command()` new; the Forth console's Enter-key handler branches on `match_run_command()` before falling through to the existing `forth_eval_line()` path; one `fs_create_file()` call seeding `/BIN/HELLO` added right after `fs_bootstrap_dirs()`. No `forth.c`/`fs.c` changes at all.

This is the first piece of "functional" content for the system folders -- `/BIN` now has a real reason to exist, not just a name. `/ETC` (real config the kernel reads back) and `/VAR` (real logging, which needs an append operation `fs.c` doesn't have yet) remain open, decomposed but not started, per this log's standing practice.

## 2026-08-15 -- /VAR/LOG: real logging, and the filesystem's first append operation

Picked up next, the last of the three "functional system folders" pieces. Needed something genuinely new at the filesystem layer, unlike `/BIN`/`/ETC` which only needed new `kernel.c` logic on top of `fs_create_file()`/`fs_read_file()`: every write in `fs.c` so far has been write-once.

**`fs_append_file(path, data, size)`, new in `fs.c`/`fs.h`.** Creates the file (delegating to `fs_create_file()`) if it doesn't exist yet, so a logger needs one call, not two separate "first write" and "later writes" paths. For an existing file, the bump allocator (no free list, no reclaim -- the same limitation `fs_delete()`'s never-reclaims-sectors gap already established) shapes what's safe: spare space in the file's own already-allocated last sector is always filled first (a single sector read-modify-write, safe regardless of what else is on disk, since those bytes are already owned by this file). Growing onto *more* sectors only happens when this file's data is still the very last thing the allocator has handed out (`start_lba + old_sectors == sb.next_free_lba`) -- otherwise something else already occupies the sectors right after it, and the append is refused (`-1`) rather than attempting a relocate-and-copy this allocator can't support. A failure between writing the tail sector and updating `size_bytes` leaves a few bytes physically on disk but past what the metadata claims -- harmlessly orphaned (invisible to `fs_read_file()`), not corrupting anything previously readable.

**`/VAR/LOG`, one line per boot, `ATA: <status> FS: <status>`** (`ata_status`/`fs_status` already read `"ATA: ..."`/`"FS: ..."`, so no extra labeling needed) -- appended right after `ata_selftest()`/`fs_selftest()` run. This is the one piece of "functional content" that's genuinely real over time in a way `/BIN`'s seeded script and `/ETC`'s seeded config aren't: it grows on its own, unattended, across every future boot, with no seeding trick needed.

**Verified against real repeated reboots, not scratch-image byte editing** -- the first time in this project's "functional system folders" work that didn't need it, since appending across real boots *is* the feature. Booted a disposable scratch copy of `fs.img` four times in a row, parsing the on-disk root -> `/VAR` -> `LOG` chain directly after each boot (same technique validated in the Unix-like-folders review): boot 1 created `LOG` at 15 bytes (one line); boots 2-4 each grew it by another 15 bytes (30, 45, 60), `start_lba` unchanged throughout -- confirming the tail-fill path, not a relocate, is what's actually happening. Cross-checked through the real UI too: raised the FILES window, navigated into `/VAR`, confirmed `LOG 60B` listed, clicked it, and the VIEWER showed all four accumulated lines correctly.

**Left to code review, not exercised on screen**: the "extend past the current sectors" branch (needs `~35+` boots to fill a fresh 512-byte sector's `ATA: OK FS: OK\n` capacity) and the tail-refusal path (needs something else allocated after `/VAR/LOG` before it needs to grow again) -- both real, both correctly shaped by the code, neither practical to trigger by hand in one verification pass. Same "code review covers the untestable case" precedent Stage D of the file manager set for its non-empty-directory delete refusal.

Files: `kernel/fs.h`/`.c` (`fs_append_file()`, new); `kernel/kernel.c` (one `fs_append_file()` call building and appending the boot log line, right after `fs_bootstrap_dirs()`).

This closes out the three-piece "functional system folders" request from earlier today: `/BIN` (RUN, executing real scripts), `/ETC` (real config the kernel reads back), `/VAR` (real logging that grows on its own). `/HOME` and `/USR` remain untouched scaffolding -- nothing has asked for them yet.
