# acid OS v2 — audio subsystem design

Date: 2026-09-14
Status: approved design, pending spec self-review sign-off

## Context

Bring-up (phase 1) and windowing (phase 2, PR open, not yet merged) are done. This spec covers phase 3: a real, machine-wide audio output path — apps can trigger notes on RaveOS v1's own 8-voice SID-style synth, real audible sound comes out on `sim`, and the whole thing is fault-contained the same way windowing's own window/queue leak was (an app that crashes mid-note doesn't leave a stuck tone playing forever).

**This phase is modeled on family-mruby-os's real audio architecture**, the same way windowing was modeled on their real windowing architecture — `family-mruby/fmruby-core` was re-cloned and its audio source read directly (`main/prebuild_scripts/kernel/fmrb_kernel/audio_handler.rb`, `lib/add/picoruby-fmrb-app/mrblib/fmrb-audio.rb`), not assumed from the earlier windowing research. Facts below marked **[confirmed]** come from reading that source; this project's own choices are marked **[this project]**.

**[confirmed]** Their kernel does zero audio mixing or rendering itself — it is purely a message forwarder. Apps call a Ruby method (`audio.note_on(channel, freq, volume, duty, sweep)` / `audio.note_off(channel)`), which sends an IPC message to the kernel; the kernel packs it into a compact binary protocol and forwards it to a separate, dedicated, privileged "host" task that owns the actual hardware output and a shared 4-channel NES-APU-style synth. **There is exactly one shared, machine-wide audio resource** — not one per app, not one per window — explicitly stated in their own source comments ("There is one PCM stream for the whole machine"). Multiple apps' `note_on`/`note_off` calls all write into the same shared channel state. The kernel tracks which pid triggered which note/song/WAV so that if that app dies without cleaning up (an unhandled exception, or being killed), the kernel force-silences whatever it left playing (`silence_notes_for`/`stop_music_for`/`stop_wav_for`) — the exact same shape of problem windowing already solved for orphaned windows (an app-exit path other than the deliberate one leaving a resource stuck forever), just for audio voices instead of windows.

**[confirmed]** Their actual audio stack is far larger than this project needs: an NES APU emulator (`nofrendo`'s `nes_apu.c`), an FM-synthesis sequencer format (FMSQ) with its own player, full MIDI support (SMF playback, serial MIDI, MML), WAV playback, and TTS services, all running on a dedicated hardware-specific audio task (`main/drivers/audio_p4/`). **[this project]** None of that is in scope here — this project already has its own self-contained synth (`kernel/audio/synth.c`, an 8-voice SID-style software synth, explicitly earmarked for v1→v2 reuse since the very first bring-up brainstorming session), and reuses it verbatim rather than adopting family-mruby-os's own NES-APU-based engine. What's adopted from their design is the *shape* — one shared, kernel-tracked audio resource, apps talk to it via a message/command channel, crash-triggered cleanup — not their specific synth engine or protocol.

## Decisions made during brainstorming

- **Engine:** verbatim port of `kernel/audio/synth.c`/`kernel/audio/synth.h` (RaveOS v1's own 8-voice SID-style synth) — confirmed to have zero OS dependencies (only `#include "synth.h"`, no floating point, no kernel calls), so no adaptation is needed beyond copying the files. Same engine as v1, not a rewrite, per explicit instruction.
- **Ruby API scope for this phase — deliberately minimal, matching bring-up's and windowing's own vertical-slice discipline:** `acid_play_note(voice, ona, volume)` / `acid_stop_note(voice)` only. `synth.c`'s much richer feature set (waveform selection, ADSR envelopes, the shared state-variable filter, ring modulation, per-voice arpeggios) stays available in the ported C code but is **not** exposed to Ruby yet — every voice uses a fixed, sensible default waveform/envelope for this phase. Revisit once phase 4's actual first app/game needs finer control; exposing it piecemeal now, before a real consumer exists, would be exactly the kind of premature API surface this project has avoided at every prior phase.
- **One shared resource, not per-app** — matches family-mruby-os's own explicit design and `synth_voices[SYNTH_NUM_VOICES]`'s own existing shape (already a single global array in the ported C, not something that needs per-app instancing).
- **`hw` target:** a stub, matching `hal_display_hw.c`'s existing precedent from bring-up — logs only, no real I2S output. Real hardware audio output is real hardware-bring-up work (roadmap phase 5), not this phase; no Tab5 board exists yet to test a real I2S driver against regardless.
- **Verification method — a genuine one, not just "didn't crash":** SDL2's `disk` audio driver (confirmed working on this machine: `SDL_AUDIODRIVER=disk` writes real, raw PCM output to a file instead of requiring an actual audio device) lets this phase be verified the same way every prior phase was — by inspecting real, generated output — even in this headless environment.

## Architecture

**`v2/core/audio/synth.c`, `v2/core/audio/synth.h` (new).** A verbatim copy of `kernel/audio/synth.c`/`.h` — no modifications. `synth_render_half(unsigned char *buf, unsigned int len)` fills `len` bytes of 8-bit unsigned PCM (128 = silence) at `SYNTH_SAMPLE_RATE` (22050 Hz), advancing every voice's oscillator/envelope by one sample per byte and mixing all 8 voices together — a pull-model "fill this buffer" function that maps directly onto SDL2's own audio callback shape (verified against the real vendored header: `typedef void (SDLCALL *SDL_AudioCallback)(void *userdata, Uint8 *stream, int len)` in `/usr/include/SDL2/SDL_audio.h`).

**`v2/core/kernel/kernel_audio.h`/`.c` (new).** Owns the single shared audio-command queue and per-voice ownership tracking — the audio-domain equivalent of `kernel_window.c`, but for one shared resource instead of a per-app list. A `struct audio_command { int type; int voice; int ona; int volume; void *owner_task; }` (type is `AUDIO_CMD_NOTE_ON` / `AUDIO_CMD_NOTE_OFF` / `AUDIO_CMD_RELEASE_OWNER`) flows through one `QueueHandle_t`, created once at boot by `kernel_audio_init()` (called from `sim_main.c`'s boot sequence, alongside the existing `gfx_init()`/`kernel_window_init()` calls, before any app spawns — same ordering discipline windowing's own `gfx_init` race fix established).

**Critical safety property, learned directly from windowing's own final-review finding (the shared-`LGFX`-object data race):** `synth_voices[]` and the per-voice ownership table (`void *voice_owner[SYNTH_NUM_VOICES]`) are touched **only** by the code that drains the command queue — which runs exclusively on the SDL audio callback's own dedicated thread (see below). Any app task calling `acid_play_note`/`acid_stop_note` only ever *enqueues* a command; it never touches synth state directly. This avoids reintroducing the exact class of unsynchronized-cross-task-access bug windowing had to find and fix with a mutex — here, the queue itself is the serialization point, so no separate lock is needed for `synth_voices[]`/`voice_owner[]`.

`kernel_audio_release_owner(void *owner_task)` (called synchronously from `vm_host_task`'s existing unconditional per-app cleanup, alongside the window-unregister and queue-delete calls windowing's own leak fix already added there) does **not** touch `voice_owner[]` directly — for the same safety reason. It enqueues one `AUDIO_CMD_RELEASE_OWNER` command; the audio thread's own drain loop, on seeing it, scans its own `voice_owner[]` (safe — it's the only thread that ever touches it), calls `synth_gate_off()` on every voice that task owned, and clears those entries. This mirrors family-mruby-os's `silence_notes_for(pid)` exactly, adapted to this project's queue-based, single-thread-owns-the-state discipline instead of their kernel-tracks-a-pid-set-directly approach.

**`v2/core/hal/hal_audio.h` (new) + `v2/sim/hal_audio_sim.c` (new — plain C, not C++, since SDL2's audio API is a standard C API requiring no C++, unlike LovyanGFX's templated drawing API).** `hal_audio_init(void)` calls `SDL_InitSubSystem(SDL_INIT_AUDIO)` — confirmed necessary and not already done: bring-up's `Panel_sdl::main()` only calls `SDL_Init(SDL_INIT_VIDEO)`, verified directly against the vendored `v2/components/lovyangfx/src/lgfx/v1/platforms/sdl/Panel_sdl.cpp:266` — then opens an `AUDIO_U8`, mono, `SYNTH_SAMPLE_RATE`-Hz device via `SDL_OpenAudioDevice`, with a callback that drains `kernel_audio`'s queue (applying each command to `synth_voices[]`/`voice_owner[]`) and then calls `synth_render_half()` to fill the requested buffer, then unpauses the device (`SDL_PauseAudioDevice(dev, 0)`) to start playback. The exact buffer-size (`SDL_AudioSpec.samples`) tradeoff between choppiness (too small) and note-trigger latency (too large) is a plan-time/implementation-time tuning detail, not a spec-level decision — start from a conservative value and adjust if real playback under this project's own headless-CI-style testing shows problems.

**`v2/hw/main/hal_audio_hw.c` (new).** A stub, matching `hal_display_hw.c`'s existing pattern exactly — logs via `ESP_LOGI` that it's a stub, does nothing else. Real I2S output is roadmap phase 5 (real hardware bring-up), not this phase.

**`v2/core/bindings/audio_binding.h`/`.c` (new).** `Kernel.acid_play_note(voice, ona, volume)` / `Kernel.acid_stop_note(voice)`, mruby module functions matching the existing binding pattern (`gfx_binding.c`, `event_binding.c`, `chrome_binding.c`). Each reads the calling app's own task handle via FreeRTOS's `xTaskGetCurrentTaskHandle()` (no new field needed in `kernel_app_context` — this is orthogonal to the window-geometry state that struct already carries) and calls `kernel_audio_enqueue_note_on`/`_note_off`, which push onto the one shared queue (non-blocking send, same "best-effort, latest matters more than a guaranteed history" philosophy windowing's own per-tick MOVED events use — a dropped note-on under extreme load is an acceptable, rare degradation for this phase, not something worth a stronger delivery guarantee the way windowing's *final* drag position needed one).

## Data flow — one note

1. An `AcidApp` script calls `acid_play_note(3, 49, 80)` (voice 3, ona 49 = A4 = 440 Hz, volume 80).
2. `audio_binding.c`'s binding reads its own task handle, builds an `AUDIO_CMD_NOTE_ON` command, and enqueues it onto `kernel_audio`'s shared queue (non-blocking).
3. On its own schedule (whenever SDL next calls the audio callback needing more samples — typically every few milliseconds, driven entirely by SDL's own audio thread, not by app activity), `hal_audio_sim.c`'s callback drains every pending command from the queue: for the `NOTE_ON` command, it calls `synth_set_ona`/`synth_gate_on`-equivalent setup on `synth_voices[3]` and records `voice_owner[3] = <that app's task handle>`.
4. The callback then calls `synth_render_half(stream, len)`, which advances every active voice's oscillator/envelope for this buffer's worth of samples and mixes them — voice 3 is now audible.
5. If the app later calls `acid_stop_note(3)`, the same path applies `AUDIO_CMD_NOTE_OFF` (gates the voice's envelope into release) and clears `voice_owner[3]`.
6. If the app instead crashes or exits without calling `acid_stop_note`, `vm_host_task`'s existing unconditional per-app cleanup enqueues `AUDIO_CMD_RELEASE_OWNER` for that task; the next time the audio callback drains the queue, it finds voice 3 (and any other voice that app owned) still attributed to the now-dead task, silences it, and clears the ownership entry — the note does not sound forever.

## Error handling (this phase's scope)

Matches windowing's own established minimalism: no voice-allocation pooling — an app that calls `acid_play_note` on a voice another app is already using simply steals it, the same "last write wins" simplicity `synth_voices[]`'s own single-global-array design already implies, and matching family-mruby-os's own explicit channel-numbering model rather than an auto-allocated pool (their own source is explicit that this same cross-app interference is an accepted, understood limitation of a shared-resource model with no reservation system: "the next app to play music lands on the same APU instance, where two players write the same registers and neither tune survives").

**Ambiguity closed explicitly, since "last write wins" alone doesn't fully specify this:** `acid_stop_note(voice)` is unconditional — it gates off whichever voice is *currently* playing there, regardless of which app is calling. If app A starts a note on voice 3, app B then steals voice 3 with its own note (overwriting `voice_owner[3]` to B), and app A later calls `acid_stop_note(3)` (believing it still owns that voice), app B's note stops — not app A's, which B's own steal already silently replaced. This is consistent with the whole shared-resource model this phase adopts, not a special case: the crash-cleanup path (`AUDIO_CMD_RELEASE_OWNER`) is scoped correctly regardless, since it only ever releases voices `voice_owner[]` currently attributes to the exiting task — a voice that was stolen away is, by then, already correctly attributed to its new owner and untouched by the original owner's exit.

The one real fault-containment property this phase does implement is the crash-cleanup path in the Data Flow section above — an app's *currently-owned* voices don't outlive the app.

## Testing / definition of done

Same discipline as bring-up and windowing: no automated test suite, "it produces real output, verified by inspecting it" — but audio needs its own verification shape, since there is nothing to screenshot. This phase uses SDL2's `disk` audio driver (confirmed real and working on this machine: setting `SDL_AUDIODRIVER=disk` before running `acidos_sim` writes actual generated PCM to a file instead of requiring a real audio device) as the equivalent of bring-up's screenshots and windowing's pixel-sampling — inspect the resulting raw file's bytes for genuine non-silence audio data with the right characteristics (non-128 bytes present, roughly the right count for the requested note's duration), not just "the process didn't crash."

Done when, on `sim`:
- `acid_play_note`/`acid_stop_note` are callable from an `AcidApp`-based script (extend one of windowing's existing demo apps — e.g. `demo_touch.rb` also plays a note on touch — rather than adding a new demo app for this alone, matching this phase's own minimal-API philosophy).
- Running under `SDL_AUDIODRIVER=disk` and triggering a note (via the same real `xdotool` touch interaction windowing's own tasks used) produces a disk-audio file containing genuine, non-silence 8-bit PCM data — inspected directly, not assumed.
- An app that plays a note and then closes (via the close-button path, or by crashing) does not leave that voice sounding forever — verified by triggering a note, closing/killing the app, and confirming the disk-audio output returns to silence rather than continuing to render the note.
- `hw`'s stub (`hal_audio_hw.c`) is added to its build the same way `hal_display_hw.c` was, so `hw` isn't left behind — `idf.py build` itself remains unverifiable on this machine (no ESP-IDF installed), the same carried-forward gap from bring-up and windowing, now three phases deep.
